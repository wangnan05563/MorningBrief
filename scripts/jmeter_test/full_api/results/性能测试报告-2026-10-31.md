## 1. 测试范围、模型与方法

### 1.1 接口全集与覆盖

对路由清单做自动盘点，共 **243 个 API 端点**，按调用副作用分为 7 类：

| 类别 | 数量 | 执行方式 |
|---|---:|---|
| 读接口（read，GET/无副作用） | 99 | JMeter 基线 + 阶梯 + soak |
| 外呼类（external，LLM/TTS/COS/微信/升级下载） | 60 | 单发探针（不真正触发外呼） |
| 参数校验类（validation） | 34 | JMeter 基线（残缺 JSON 走 4xx 分支） |
| 破坏性（destructive） | 30 | 单发探针（不存在的 id / 空列表） |
| 写接口（write，17 个） | 17 | 基线 + 阶梯 + soak（真实夹具数据） |
| 仅静态核对（probe，登出） | 2 | 不执行，避免使测试令牌失效 |
| SSE | 1 | 单发探针 |

覆盖结论：**150 个端点进入 JMeter 批量流量，55 个端点单发探针，35 个会触发真实外呼的端点仅做路由级静态核对（不产生出站流量），1 个 SSE 探针，2 个登出接口按设计不执行** —— 241/243 有实测或静态证据，2 个为刻意排除。逐接口明细见 [附件 A：逐接口基线指标](appendix_endpoints.md) 与 `results/per_endpoint.csv`。

### 1.2 并发模型（贴近业务而非理论峰值）

| 场景 | 线程模型 | 负载构成 |
|---|---|---|
| 基线 | 1 线程 × 3 轮 | 全部可执行端点各跑 1 次 |
| C 端读阶梯 | 10 / 50 / 100 / 200 线程，各 90 s | `episodes/today`×5、`episodes/{id}`×3、favorites/subscriptions/comments/progress 读等（按真实浏览比例加权） |
| C 端写阶梯 | 10 / 25 / 50 线程，各 90 s | 进度上报×8、评论×4、收藏增删×2+2、订阅×1+1、反馈×1、资料×1 |
| 管理端读阶梯 | 10 / 25 / 50 线程，各 90 s | 仪表盘/审核/队列/素材/统计等后台只读页面 |
| 4 h soak | C 端 14 个端点 + 管理端 6 个端点，固定线程持续 4 h | 以“上班时段正常并发”为基准的混合负载 |

### 1.3 指标口径

- **响应时间**：最近秩法 P90/P95/P99；Avg 为算术平均。
- **错误率**：与期望状态码不符的比例（如参数校验端点返回 400 属预期，不计错）。
- **缺陷率**：仅统计 **5xx 与连接失败（000）**，与“预期 4xx”严格区分。
- **拐点**：相邻档位吞吐增幅 <15% 且 P95 涨幅 >50%，或出现 5xx/连接失败。
- **资源**：2 s 采样的进程 CPU、RSS/峰值工作集、句柄数、SQLite/WAL 体积、磁盘 I/O、磁盘余量（`monitor.py`，Windows psapi/kernel32）。

## 3. 压力测试（阶梯压测与拐点）

### 3.1 C 端读

| 线程 | RPS | Avg | P95 | P99 | 错误率 | 缺陷 |
|---:|---:|---:|---:|---:|---:|---:|
| 10 | 89.6 | 103 ms | 389 ms | 1444 ms | 0.00% | 0 |
| 50 | 111.8 | 413 ms | 1118 ms | 3914 ms | 0.00% | 0 |
| 100 | 119.5 | 777 ms | 2239 ms | 12880 ms | 0.00% | 0 |
| 200 | 123.7 | 1501 ms | 4619 ms | 19874 ms | 0.00% | 0 |

**拐点 @ 100 线程**（RPS 仅 +6.9%，P95 翻倍）。峰值 123.7 RPS @200 线程，但此时 P95 4.6 s、P99 19.9 s，已不可用。资源侧：单 worker CPU 打满约 1 核（soak 均值 93.6%、峰值 183%），属 **CPU 饱和型拐点**；错误率始终 0%，说明系统靠排队保正确性，代价是延迟失控。

### 3.2 C 端写

| 线程 | RPS | Avg | P95 | P99 | 错误率 | 缺陷 |
|---:|---:|---:|---:|---:|---:|---:|
| 10 | 13.4 | 703 ms | 2581 ms | 3342 ms | 0.00% | 0 |
| 25 | 12.4 | 1937 ms | **6476 ms** | 8127 ms | 0.00% | 0 |
| 50 | **3.0** | **16653 ms** | **23564 ms** | 26981 ms | 0.00% | 0 |

**拐点 @ 25 线程**，到 50 线程吞吐反而崩塌到 3 RPS、平均 16.7 s。写负载中占比最高的是进度上报（权重 8/19），而每次进度上报都要同步等待 COS 网络超时；线程被长时间占住，形成“越压越慢”的负反馈。服务端日志同时出现 `qcloud_cos ... put_object` 连续刷屏与 `urllib3 Connection pool is full, discarding connection ... size: 10`，可确认是 **外呼阻塞 + 连接池耗尽**，而非 SQLite 写锁本身。

### 3.3 管理端读

| 线程 | RPS | Avg | P95 | P99 | 错误率 | 缺陷 |
|---:|---:|---:|---:|---:|---:|---:|
| 10 | 34.6 | 268 ms | 554 ms | 928 ms | 0.00% | 0 |
| 25 | 64.3 | 363 ms | 703 ms | 983 ms | 0.00% | 0 |
| 50 | 72.6 | 637 ms | 1230 ms | 1683 ms | 0.00% | 0 |

**拐点 @ 50 线程**（RPS +13%，P95 +75%）。管理端单条查询更重（审核详情、统计），在同样单 worker 下更早触顶。

### 3.4 压力期资源水位

| 指标 | 基线 | 压力峰值 |
|---|---:|---:|
| RSS | 139→164 MB | 151→244 MB（max 266.8 MB） |
| CPU | 均值 11.9% | 均值 39.2%，峰值 172.2% |
| 句柄 | ≤472 | **2024**（连接抖动/短连接 FD 峰值） |
| 磁盘余量 | 1.99 GB | **1.67 GB** |

错误率在所有档位均为 0%，**容量上限以延迟而非 5xx 的形式表现**；因此线上应使用“P95 预算”而不是错误率作为扩容信号。
测试过程中沙箱进程曾随 JMeter 编排任务一起被外部终止（非服务自身崩溃，日志无异常栈），已重建沙箱并补跑缺失档位，上表为补跑后的完整数据。

## 4. 稳定性测试（4 h Soak）

### 4.1 第一轮（C 端 4 h / 管理端 2 h）

| 窗口（30 min） | C 端 RPS | C 端 P95 | 错误率 | 管理端 RPS | 管理端错误率 |
|---:|---:|---:|---:|---:|---:|
| W0 | 132.3 | 480 ms | 0.00% | 16.4 | 0.00% |
| W7 | **59.5** | **1787 ms** | 0.00% | 131.7 | **100%（401）** |

- **C 端**：1,303,532 样本、**0 缺陷**，但吞吐从 132.3 衰减到 59.5 RPS（-55%），P95 每窗口 +194 ms。
- **端点级退化**（末窗 P95 > 首窗 1.5 倍）**只出现在两个接口**：
  - `GET /api/v1/playlogs/progress/{episode_id}`：611 → **6160 ms**
  - `POST /api/v1/playlogs/progress`：578 → **5255 ms**
  - 其余 12 个 soak 端点（今日节目、收藏、订阅、评论等）P95 波动在 200–700 ms，无单调退化。
- **管理端**：前 2 小时 0 错误，之后全部 401 —— 原因是测试令牌有效期 2 h（`JWT_ADMIN_EXPIRE_HOURS=2`），**属测试装置问题，不是系统缺陷**。修正后（沙箱 `env_overrides` 将令牌延长到 8 h）重跑的管理端基线与 3 档阶梯错误率均为 0，已确认 401 不再出现；4 h 进程级泄漏结论以 C 端同进程 soak 为准（两者共用同一 worker、同一连接池与同一数据库），故管理端不再单独重复 4 h 空跑。

### 4.2 资源长稳结论（第一轮 4 h）

| 指标 | 4 h 结果 | 判定 |
|---|---|---|
| CPU | 均值 93.6%，峰值 183.3% | **单 worker 长期打满 1 核**，是读吞吐的天花板 |
| RSS | 182.3 → 198.6 MB（max 200.8，峰值工作集 286.4） | 进入平台期，斜率 +0.0013 MB/采样 → **无内存泄漏** |
| 句柄 | max 623，斜率 +0.0012/采样 | **无句柄泄漏** |
| SQLite | 35.6 → 40.8 MB（+5.2 MB，写入导致），WAL ≤4.2 MB 稳定 | **无 WAL 膨胀** |
| 磁盘余量 | 最低 1.54 GB（D: 99% 已用） | **风险项**：不足以支撑更大 JTL/备份 |
| 磁盘 I/O | 读均值 3.85 MB/s，写均值 65 KB/s | 非瓶颈 |

### 4.3 退化根因链

`POST /playlogs/progress` → `cos_client.put_object()`（未判断 COS 是否配置）→ `asyncio.to_thread` 中的同步 HTTPS 请求 → 沙箱无凭据/无外网时等 TCP 超时 → 占用线程与 urllib3 连接池 → 写线程池被耗尽 → **固定线程数的 soak 中 RPS 单调下滑，且只影响进度读写**。这与 3.2 的写压测崩塌是同一根因，证据相互印证。

## 6. 优化建议清单

### 6.1 代码逻辑精简

| 优先级 | 优化内容 | 预期收益 |
|---|---|---|
| **高** | 在 `play_service.report_progress` / `get_progress` 入口增加 `is_cos_configured()` 判断；未配置时直接走本地 SQLite/缓冲，不发任何出站请求 | 写 P95（25 线程）**6476 ms → 150–250 ms**；写吞吐 **12.4 → 150+ RPS**；4 h soak 不再衰减（132 RPS 保持平稳）。这是全报告收益/成本比最高的一项 |
| **中** | 进度上报改为“写缓冲 + 定时/阈值落库”（如每 5 s 或每 10% 变更），读路径允许 2–3 s 本地缓存 | 进度写 RPS 提升 3–5 倍，SQLite 写放大下降一个量级 |
| **中** | `delete_script` 删除前检查 `episode/review` 引用，返回 409 + 可选“强制级联”；或将外键改为 `ON DELETE SET NULL` | 500 → 409，消除探针发现的唯一 5xx |
| **中** | bcrypt 校验放入专用线程池并适度降低 cost（12→10，需安全评估）；登录失败计数走缓存 | 登录 P95 931 ms → ~250 ms |
| **低** | `favorites.add_favorite` 在锁内一并取回 `id`，或改用 `INSERT ... RETURNING` | 消除 B10 的 500 潜在路径 |

### 6.2 缓存策略调整

| 优先级 | 优化内容 | 预期收益 |
|---|---|---|
| **高** | 进度读：命中未配置 COS 时直接读 SQLite；已配置时也加 2–3 s 进程内缓存并合并并发请求 | 进度读 P95 6160 ms（soak 末窗）→ <100 ms |
| **中** | `ebooks` 分类：超时 40 s → 5 s；失败写入 60 s 负缓存；应用启动预热 README | 冷启动 22.5 s → ≤5 s，且失败不再反复拖慢 |
| **中** | 管理端仪表盘/统计类接口加 15–30 s TTL（当前无缓存） | 管理端读 P95 1230 ms → ~400 ms |
| **低** | `episodes/today`、列表缓存命中率埋点，按真实热点调整 TTL（当前 3600/600 s 偏保守） | 降低 DB 读压力 20–30% |

### 6.3 数据库查询优化

| 优先级 | 优化内容 | 预期收益 |
|---|---|---|
| **中** | 审计日志与业务写同事务提交，改为写后异步落审计（或批量） | 写事务时长缩短 30–50%，写吞吐提升 |
| **中** | 为 `play_log(user_id, episode_id)`、`favorite(user_id, episode_id)`、`script(workflow_id)` 确认复合索引并补 `EXPLAIN` 回归 | 进度/收藏读写 P95 降低 20–40% |
| **低** | `db-admin` 全表统计/导出走只读连接并限流、分页 | 避免管理端重查询挤占写锁 |
| **低** | 清理历史 `play_log`（按月归档） | DB 从 40.8 MB 回落，长稳期磁盘增长可控 |

### 6.4 连接池配置调优

| 优先级 | 优化内容 | 预期收益 |
|---|---|---|
| **高** | COS/HTTP 客户端：配置 `PoolManager(maxsize=50)`、连接/读超时 2–3 s、失败快速熔断；或在未配置时根本不建客户端 | 消除 `Connection pool is full` 告警与线程饥饿 |
| **中** | SQLite 池 20+100 对单 worker 明显过大，建议 5+10；同时关闭每请求 `pre_ping`（本地文件不需要） | 句柄峰值 2024 → <300；单请求省 1 次往返 |
| **低** | 为慢查询设置 `busy_timeout` 分层（读 2 s / 写 10 s），避免长事务拖住整个写队列 | 写尾延迟更稳 |

### 6.5 负载均衡 / 部署架构

| 优先级 | 优化内容 | 预期收益 |
|---|---|---|
| **高** | 扩容前先解决 B4：把进程内 `asyncio.Lock` 换成 **DB 级互斥**（`BEGIN IMMEDIATE` 或 Postgres 行锁/`pg_advisory_lock`），然后 `UVICORN_WORKERS=4` 或多实例 + Nginx | 读吞吐 120 → **400+ RPS**；P95 在 200 线程下从 4.6 s 回落到亚秒级 |
| **中** | 写路径迁到 PostgreSQL（SQLite 单写者与多实例天然冲突） | 写吞吐从 13 → 数百 TPS，支撑水平扩容 |
| **中** | Nginx `keepalive`/`upstream` 健康检查 + 请求体/超时统一（当前直连 uvicorn） | 消除单点，滚动发布不掉流量 |
| **低** | 增加“P95 预算”告警（而非仅错误率）与慢接口 Top-N 看板 | 在延迟劣化早期发现容量问题 |

## 7. 整体结论

### 7.1 健康度评估

- **读路径：低并发健康，容量有硬顶。** 单并发 P95 99 ms，错误率 0；但单 worker 在 ~120 RPS 即 CPU 饱和，P95 随并发线性恶化，200 线程时 P99 19.9 s。
- **写路径：不健康。** 进度接口的 COS 外呼把写混合压到 13 RPS（50 线程时 3 RPS）；4 h soak 中吞吐腰斩、只有进度接口退化，根因单一且明确。
- **长稳：无资源泄漏。** 4 h 内 RSS/句柄/WAL 全平台化；但磁盘余量 1.5 GB 是运维级风险。
- **正确性：基线/压力/soak 缺陷率均为 0；** 唯一 5xx 来自探针命中的删稿外键冲突（B5）。

综合评级：**读路径 B（可用但有瓶颈），写路径 D（瓶颈显著），稳定性 B（无泄漏但存在确定性退化），运维风险 C（磁盘余量）**。

### 7.2 Top 3 问题

1. **进度读写无条件调用 COS（B2/B3）** —— 单点即可造成写吞吐崩塌与 4 h 退化，修复成本极低（一个配置判断 + 超时/熔断），应最先处理。
2. **单 worker + 进程内写锁 + SQLite 单写者（B1/B4）** —— 决定了系统 120 RPS 的读上限与 13 RPS 的写上限，是扩容的结构性障碍；必须先做跨进程互斥再谈多 worker。
3. **外呼型冷缓存与慢操作（B6/B7）+ 磁盘余量（B9）** —— 22.5 s 的管理端冷启动、0.9 s 登录与仅 1.5 GB 的磁盘余量，分别影响体验与可持续性，属于短期即可显著改善的“低垂果实”。

### 7.3 短期路线（4 周）

| 周 | 动作 | 验收标准 |
|---|---|---|
| W1 | P0：COS 配置判断 + 超时/熔断；清理历史 JTL/日志释放磁盘；删稿 409 化 | 25 线程写 P95 <250 ms；soak 4 h RPS 无下滑；磁盘余量 >5 GB |
| W2 | P1：进度写缓冲 + 读缓存；SQLite 池缩容、关 pre_ping；ebooks 超时/负缓存/预热 | 进度读 P95 <100 ms；管理端冷启动 ≤5 s；句柄峰值 <300 |
| W3 | P1：跨进程写互斥（DB 锁）+ 多 worker 试点；bcrypt 线程池 | 读 200 线程 RPS ≥300，P95 <1 s；登录 P95 <300 ms |
| W4 | P2：PG 迁移评估/灰度；管理端统计缓存；P95 预算告警与慢接口看板 | 全量回归 + 4 h soak 复测通过 |
