- 响应时间：最近秩法 P90/P95/P99；Avg 算术平均。

**按 §1.3 判据的拐点在 50 线程**（10→50 吞吐 −1.4%、P95 80→380 ms），但**吞吐峰值出现在 10 线程即触顶**：

超出上限后系统靠排队保正确性，代价是延迟线性失控，而错误率始终 0%。

  W7 立刻回到 168.2 RPS（全场最高），确认无单调衰减。**长跑结论：机器需独占。**

## 6. 优化建议（按收益/成本排序，目标值以本批数据为基准）

### 6.1 代码逻辑精简

| 优先级 | 动作 | 量化预期 |
|---|---|---|
| **P0** | `report_progress`/`get_progress` 入口先判 `is_cos_configured()`，未配置直接跳过（不发请求、不进异常路径）；已配置则把 COS 写移出请求路径（后台队列） | 配置 COS 的真实环境：进度写 P95 由 1117 ms（10-31 实测）回到本批的 **≤37 ms** 水平；消除 soak 末窗 5255 ms 退化 |
| **P0** | 修 B4：在写锁内取回 `id`（或 `INSERT ... RETURNING`），并把 `NoResultFound` 转 409 | 本批唯一 5xx 归零（0.1–0.18% → 0） |
| **P1** | 评论/收藏/订阅/反馈也走缓冲或按表分锁，缩小临界区 | 写触顶值 126 → **200+ RPS**（CPU 尚有 14% 余量） |
| **P1** | `delete_script` 删除前检查 `episode/review` 引用 → 409（或外键改 `ON DELETE SET NULL`） | 消除 B11 的 500 |
| **P2** | bcrypt 放专用线程池并评估 cost 12→10 | 登录 P95 731 ms → ~250 ms |
| **P2** | 统一 B10：业务 `code` 映射到 HTTP 状态码 | 使错误率/熔断可按状态码消费 |

### 6.2 缓存策略

| 优先级 | 动作 | 量化预期 |
|---|---|---|
| P1 | `ebooks` 索引常驻内存 + 构建完成后热替换（当前每请求扫 23 338 条） | `search` 195→≤20 ms、`random` 162→≤10 ms |
| P1 | 索引缺失/过期时的构建加**负缓存 + 启动预热 + 超时 40→5 s** | 消除 935 s 后台抓取窗口；生产"找书"首开不再阻塞 14 天一次 |
| P2 | 管理端仪表盘/统计 15–30 s TTL；进度读 2–3 s 进程内缓存 | 管理端读 P95 895→~450 ms；读触顶 275→~330 RPS |
| P2 | 把 `cases.json` 的 `external` 判定改为按代码路径扫描（含间接外呼） | 覆盖率分类不再漏判 |

### 6.3 数据库查询

| 优先级 | 动作 | 量化预期 |
|---|---|---|
| P1 | `reviews`/`workflows`/`db-admin rows` 复合索引 + `EXPLAIN` 回归 | 三者 P95 1029/860/801 ms → <500 ms |
| P2 | 审计日志改异步批量落库 | 写事务时长 −30~50%，写触顶再升 |
| P2 | 清理历史 `play_progress`/`comment`（本批沙箱 4 h 就 +7 MB） | 长稳期磁盘增长可控 |

### 6.4 连接池

| 优先级 | 动作 | 量化预期 |
|---|---|---|
| P1 | SQLite 池 20+100 → 5+10，关闭 `pool_pre_ping` | 句柄峰 1496→<300；每请求省 1 次往返 |
| P1 | COS/HTTP 客户端 `maxsize=50`、连接/读超时 2–3 s、失败熔断 | 配置 COS 时不再出现 `Connection pool is full` 与线程饥饿 |

### 6.5 负载均衡 / 部署架构

| 优先级 | 动作 | 量化预期 |
|---|---|---|
| **P0（扩容前置）** | 进程内 `asyncio.Lock` → DB 级互斥（`BEGIN IMMEDIATE`；PG 用行锁/advisory lock） | 否则多 worker 会破坏写互斥 |
| **P0** | 完成上一项后 `UVICORN_WORKERS=4` 或多实例 + Nginx | 读触顶 275 → **≈1000 RPS**（本批是干净的单核 CPU 上限，×4 线性外推可信）；200 线程 P95 1634 ms → 亚秒 |
| P1 | 写路径迁 PostgreSQL | 写触顶 126 → 数百 TPS，支撑水平扩容 |
| P2 | 增加「P95 预算」告警与慢接口 Top-N 看板 | 全档位错误率 0% 但延迟劣化 20 倍 —— 只看错误率必然漏报 |

## 7. 结论

### 7.1 健康度

- **读路径 B+**：单并发 P95 29 ms（C 端）/125 ms（管理端），4 h 零缺陷；但单 worker 在 **10 线程就触顶 ≈275 RPS**，
  CPU 饱和型拐点，200 线程 P95 1.63 s、P99 2.22 s。
- **写路径 B−**：上限 **126 RPS**，且**不是 CPU 限制**而是写锁 + 单写者；进度写已缓冲化（P95 37 ms），
  其余写接口 P95 ~900 ms。10-31 批的「写崩塌到 3 RPS」是 COS 真实配置所致，本批证明**该路径可回到毫秒级**。
- **稳定性 A−**：1 747 296 + 207 371 样本、**0 缺陷、0 错误率、无端点级退化、无内存/句柄/WAL 泄漏**；
  W5/W6 掉速已归因于并发开发挤占客户端，非服务问题。
- **正确性**：唯一 5xx 为 B4（收藏并发 `NoResultFound`，0.1–0.18%）；B11（删稿 FK 500）为代码级遗留。
- **运维风险 C**：磁盘余量 1.47 GB；**`backend/data/backup/` 为空目录**（33.4 MB 单文件库零备份）。

### 7.2 Top 3

1. **单 worker + 进程内写锁（B1/B3）** —— 决定 275 RPS 读上限与 126 RPS 写上限；先做跨进程互斥，再谈多 worker，
   收益是 3–4 倍吞吐，是全局性价比最高的一条。
2. **COS 无条件调用 + 外呼超时（B2）** —— 修复成本极低（一个配置判断 + 移出请求路径 + 超时/熔断），
   但在真实配置下决定了写路径是否可用（1117 ms vs 37 ms）与 soak 是否退化（5255 ms vs 无退化）。
3. **冷缓存窗口与资源余量（B5/B9 + 备份缺失）** —— 935 s 后台抓取能整批污染压测结论（本批就付了学费），
   磁盘 1.47 GB 与零备份随时可能让一次长跑或一次误操作不可恢复。

### 7.3 短期路线（4 周）

| 周 | 动作 | 验收 |
|---|---|---|
| W1 | P0：COS 配置前置判断 + 移出请求路径；修 B4 500；磁盘清理 + 建立备份 | 配置 COS 环境 50 线程写 P95 <200 ms；全档 0 缺陷；`backup/` 非空且磁盘余量 >5 GB |
| W2 | P0：DB 级写互斥 + `UVICORN_WORKERS=4` 试点 | 读 ≥900 RPS、200 线程 P95 <800 ms |
| W3 | P1：ebooks 索引常驻 + 预热/负缓存；SQLite 池缩容关 pre_ping；管理端统计 TTL | `search`/`random` <20 ms；句柄峰 <300；管理端 P95 <500 ms |
| W4 | P1：评论/收藏写缓冲 + 索引；P2：状态码语义统一 + P95 预算告警 | 写触顶 >200 RPS；B10 消除；4 h soak 复测 |
