# 决策逻辑详解

> 本文详解 workspace-cleanup skill 中 7 个核心判断的逻辑推导与边界处理。
>
> 决策 1-4 为基础判断，决策 5-7 为 2026-07-05 第五轮清理复盘后新增的增强判断。

---

## 决策 1：文件是否属于"垃圾"？

### 判断流程

```
输入：文件 X（path, name, ext, size, mtime）
       │
       ▼
┌─────────────────────────────────────┐
│  Q1: X 命中 garbage_patterns 吗？  │
│     (redirect_artifacts/tmps/...)  │
└─────────────────────────────────────┘
       │ Yes                │ No
       ▼                    ▼
   垃圾 ❌           ┌─────────────────────────────────────┐
                    │  Q2: X 在根目录吗？                 │
                    └─────────────────────────────────────┘
                              │ Yes                │ No
                              ▼                    ▼
                    ┌──────────────────────┐     保留 ✅
                    │ Q3: X 在白名单吗？  │
                    │ (allowed_files/      │
                    │  allowed_ext)        │
                    └──────────────────────┘
                              │ Yes      │ No
                              ▼          ▼
                          保留 ✅     垃圾 ❌（按 trash 模式）
```

### 关键边界

- **`.env` vs 异常名 `.env`**：`.env` 在白名单，但若内容是乱码则按"疑似垃圾"标红
- **空文件 (0 字节)**：默认不视为垃圾（如 `.gitkeep`），但若符合 redirect_artifacts 模式则视为垃圾
- **大文件（> 10MB）在根目录**：触发"误重定向大文件"高优先级判断，要求显式确认
- **配置未覆盖的新型文件**：进入决策 7（模式推断）

## 决策 2：文件是否属于"脚本"？

### 判断流程

```
输入：文件 X（path, name, ext）
       │
       ▼
┌─────────────────────────────────────┐
│  Q1: X.ext ∈ script_extensions?    │
└─────────────────────────────────────┘
       │ No                │ Yes
       ▼                    ▼
   非脚本 ✅       ┌─────────────────────────────────────┐
                  │  Q2: X.path 含 script_exclude_dirs?│
                  │  (如 src/, frontend/src/, tests/)  │
                  └─────────────────────────────────────┘
                              │ Yes            │ No
                              ▼                ▼
                       源码/测试 ✅      ┌────────────────────┐
                                       │  Q3: X 是配置/数据?│
                                       │  (按 content sniff)│
                                       └────────────────────┘
                                                  │ Yes       │ No
                                                  ▼           ▼
                                            非脚本 ✅      散落脚本 → Move
```

### 关键边界

- **`scripts/` 下的脚本**：已就位，不动
- **`scripts/tests/` 下的脚本测试**：是脚本的单元测试，保留
- **源码目录下的脚本**（`src/.../module.py`）：是代码模块，不算散落脚本
- **同名 .py 在 src/ 和根目录**：源码不动，根目录的若是工具脚本则 Move

## 决策 3：服务是否在运行？（三重检测 + 文件占用兜底）

### 判断流程

```
输入：service_indicators 配置
       │
       ▼
┌─────────────────────────────────────────────┐
│  检测 1: pid_files 中是否有文件存在         │
│  若有 → 读取 PID，验证进程存在             │
└─────────────────────────────────────────────┘
       │ 任意一项 Yes         │ 全部 No
       ▼                     ▼
   服务运行中 🚦         ┌──────────────────────────┐
   (停止服务 OR          │  检测 2: ports 端口监听  │
    降级到软删除)        └──────────────────────────┘
                                  │ 任意端口 Yes  │ 全部 No
                                  ▼              ▼
                            服务运行中 🚦   ┌──────────────────────────┐
                                            │  检测 3: 进程名匹配      │
                                            │  process_names /         │
                                            │  process_name_patterns   │
                                            └──────────────────────────┘
                                                  │ 任一进程 Yes  │ 全部 No
                                                  ▼              ▼
                                            服务运行中 🚦   ┌──────────────────────────┐
                                                            │  检测 4: 文件占用探测    │
                                                            │  file_occupancy_probes  │
                                                            └──────────────────────────┘
                                                                  │ 任一文件被占用 │ 全部未占用
                                                                  ▼              ▼
                                                            服务运行中 🚦   服务未运行 ✅
                                                            (间接证据，需用户确认)
```

### 关键边界

- **PID 文件存在但进程已死**：视为服务未运行，但记录"PID 文件残留"到清理报告
- **PID 文件缺失但服务实际运行**：第五轮清理发现的常见场景，靠检测 2/3/4 兜底
- **端口监听但无法获取进程**：可能是 TIME_WAIT 状态，提示用户人工确认
- **多服务并行**：以"任一服务运行"为真，全部停完才进入 Phase 4
- **文件占用作为间接证据**：run.stdout.log 被持有 → 服务在写入日志 → 视为运行中
- **文件占用检测的局限性**：仅适用于已知服务会持有的文件，需在配置中正确声明

### 检测优先级

1. PID 文件（最直接，但可能缺失）
2. 端口监听（可靠，但需配置正确端口）
3. 进程名（可靠，但跨平台命令差异大）
4. 文件占用（间接证据，作为兜底）

## 决策 4：操作是否安全？

### 判断流程

```
输入：操作 O (Delete/Move)，目标文件 X
       │
       ▼
┌─────────────────────────────────────┐
│  Q1: X 已在 backup_log 记录 hash?  │
└─────────────────────────────────────┘
       │ No                │ Yes
       ▼                    ▼
   不安全 ⛔          ┌──────────────────────┐
                    │  Q2: 服务已停止?     │
                    │  (服务运行中)        │
                    └──────────────────────┘
                              │ No        │ Yes
                              ▼           ▼
                         不安全 ⛔   ┌────────────────────┐
                                    │ Q3: 操作分类判断  │
                                    │ Delete → 在垃圾名单?
                                    │ Move   → 目标可写?│
                                    └────────────────────┘
                                              │ Yes  │ No
                                              ▼     ▼
                                          安全 ✅  不安全 ⛔
```

### 关键边界

- **Move 到 scripts/ 的目标冲突**：提示用户"文件已存在，是否覆盖"
- **Delete 大文件（> safety.large_file_threshold_mb）**：要求二次确认
- **批量操作中断**：保留 backup_log 以便恢复
- **每批删除后验证**（`safety.verify_after_each_batch: true`）：立即检查删除结果是否匹配预期

## 决策 5：后台进程是否在持续创建文件？（新增）

### 背景

第五轮清理发现：清理过程中有新文件被持续创建（如 `compare_*.ps1`、`do_git_commit.ps1`、`ubprocess; r=subprocess.run(...)`）。
这些文件来自并发的 AI 会话或后台脚本，会导致清理"复发"。

### 判断流程

```
输入：Phase 4 执行后的根目录状态
       │
       ▼
┌─────────────────────────────────────────────┐
│  Step 1: 记录 Phase 4 完成时的文件清单      │
│  snapshot_after = list_files(root)          │
└─────────────────────────────────────────────┘
       │
       ▼
┌─────────────────────────────────────────────┐
│  Step 2: 等待 stability_check.wait_seconds  │
└─────────────────────────────────────────────┘
       │
       ▼
┌─────────────────────────────────────────────┐
│  Step 3: 复扫根目录                         │
│  snapshot_now = list_files(root)            │
└─────────────────────────────────────────────┘
       │
       ▼
┌─────────────────────────────────────────────┐
│  Step 4: 比较两次快照                       │
│  new_files = snapshot_now - snapshot_after  │
└─────────────────────────────────────────────┘
       │ new_files 为空    │ new_files 非空
       ▼                   ▼
   稳定 ✅           ┌─────────────────────────────────────┐
                    │  Step 5: 匹配 recurrence_patterns   │
                    │  判断是否为已知后台进程产物         │
                    └─────────────────────────────────────┘
                              │ 匹配          │ 不匹配
                              ▼               ▼
                        已知复发 ⚠️       未知新文件 ❓
                        (按 recurrence_   (提示用户排查)
                         action 处理)
```

### 处理策略（recurrence_action）

| 策略 | 行为 | 适用场景 |
|---|---|---|
| `warn` | 仅警告，继续后续阶段 | 默认策略，复发文件不影响清理目标 |
| `stop` | 停止后续阶段，等待用户介入 | 复发文件可能影响验证结果 |
| `soft_delete` | 重命名复发文件为 `.trash` 后缀 | 用户希望立即清理但无法停止后台进程 |

### 关键边界

- **复发次数超过 max_recurrence**：强制停止，提示用户排查后台进程
- **复发文件匹配 recurrence_patterns**：视为"已知后台进程产物"，按策略处理
- **复发文件不匹配任何模式**：视为"未知新文件"，必须提示用户排查
- **stability_check.enabled: false**：跳过稳定性检查，但需在报告中标注

## 决策 6：异常文件名如何处理？（新增）

### 背景

第五轮清理发现两类异常文件名：
1. `not enabled, try to fix it now.`（含空格和句号）
2. `ubprocess; r=subprocess.run(['git','diff',...])`（含分号、引号、括号）

这些文件名含特殊字符，直接使用路径字符串会导致 PowerShell 解析错误。

### 判断流程

```
输入：文件名 X
       │
       ▼
┌─────────────────────────────────────────────┐
│  Q1: X 含特殊字符吗？                       │
│  (空格 / 分号 / 引号 / 括号 / 等号 / @)    │
└─────────────────────────────────────────────┘
       │ No                │ Yes
       ▼                   ▼
   直接路径 ✅        ┌─────────────────────────────────────┐
                      │  Q2: special_filename_handling?    │
                      │  safe: 使用 Get-ChildItem 匹配     │
                      │  direct: 直接路径（可能失败）      │
                      └─────────────────────────────────────┘
                                │ safe          │ direct
                                ▼               ▼
                          ┌─────────────────────┐  直接 Remove-Item
                          │  Get-ChildItem -File│  (可能报错)
                          │  Where-Object {     │
                          │    $_.Name -like    │
                          │    "<pattern>"      │
                          │  }                  │
                          │  → Remove-Item      │
                          │  -LiteralPath       │
                          │  $file.FullName     │
                          └─────────────────────┘
```

### 安全处理模板（safe 模式）

```powershell
# 不要直接使用路径字符串
# ❌ $p = Join-Path $root "not enabled, try to fix it now."
# ❌ Remove-Item $p  # 可能因特殊字符失败

# 使用 Get-ChildItem + Where-Object 匹配
# ✅
$odd = Get-ChildItem -Path $root -File | Where-Object { $_.Name -like "not enabled*" }
if ($odd) { Remove-Item -LiteralPath $odd.FullName -Force }
```

### 关键边界

- **通配符匹配**：使用 `-like` + `*` 匹配前缀或后缀，避免完整文件名
- **-LiteralPath**：删除时必须用 `-LiteralPath` 而非 `-Path`，防止通配符被二次解析
- **文件名含 `]` 或 `[`**：这些是 PowerShell 通配符元字符，必须用 `-LiteralPath`
- **文件名含换行符**：极少见，但需用 `Get-ChildItem` 遍历而非直接路径

## 决策 7：配置缺失时如何推断垃圾模式？（新增）

### 背景

第五轮清理发现：example 配置无法覆盖所有调试产物（如 skill 集成脚本、git 调试脚本）。
当 `garbage_patterns` 未覆盖某些文件时，基于文件名特征自动推断。

### 判断流程

```
输入：文件 X（未匹配任何 garbage_patterns）
       │
       ▼
┌─────────────────────────────────────────────┐
│  Q1: detection.enabled == true?             │
└─────────────────────────────────────────────┘
       │ No                │ Yes
       ▼                   ▼
   保留（不推断）    ┌─────────────────────────────────────┐
                    │  Q2: X.name 匹配 prefix_indicators?│
                    │  (如 "_" / ".tmp_")                │
                    └─────────────────────────────────────┘
                              │ Yes            │ No
                              ▼                ▼
                        疑似垃圾 ⚠️     ┌─────────────────────────────────────┐
                        (置信度 0.8)    │  Q3: X.name 含 name_keywords?      │
                                        │  (如 debug/diag/trace/verify)      │
                                        └─────────────────────────────────────┘
                                                  │ Yes           │ No
                                                  ▼               ▼
                                            疑似垃圾 ⚠️    ┌─────────────────────────────────┐
                                            (置信度 0.7)   │  Q4: X.name 匹配 name_patterns?│
                                                          │  (如 test_*.py / run_*.py)     │
                                                          └─────────────────────────────────┘
                                                                    │ Yes          │ No
                                                                    ▼              ▼
                                                              疑似垃圾 ⚠️      保留 ✅
                                                              (置信度 0.9)
```

### 置信度评估

| 来源 | 置信度 | 说明 |
|---|---|---|
| prefix_indicators 匹配 | 0.8 | `_` 前缀强烈暗示临时调试 |
| name_keywords 匹配 | 0.7 | 含 debug/diag 等关键词 |
| name_patterns 匹配 | 0.9 | 模式匹配（如 test_*.py）最可靠 |
| 多源同时匹配 | 1.0 | 两个以上特征同时命中 |

### 关键边界

- **置信度低于 infer_confidence_threshold**：仅标记为"疑似垃圾"，需用户确认
- **置信度高于阈值且 auto_add_inferred_to_gitignore: true**：自动将推断模式加入 .gitignore
- **推断模式不自动加入 garbage_patterns**：避免污染配置，仅用于本次清理
- **白名单优先**：即使匹配推断模式，若文件在 root_allowlist 中则保留

### 推断模式示例

```yaml
# 第五轮清理中通过推断识别的模式（已加入 .gitignore）
detection:
  name_patterns:
    - "test_*.py"        # 临时测试脚本（非 tests/ 目录）
    - "run_*.py"         # 临时运行脚本
    - "run_*.js"         # 临时运行 JS
    - "git_*.py"         # git 调试脚本
    - "verify_*.py"      # 验证脚本
    - "_*.log"           # _ 前缀日志
```

## 决策总结

| 决策 | 输入 | 输出 | 配置依赖 |
|---|---|---|---|
| 1. 是否垃圾 | 文件元数据 | Delete / Keep | garbage_patterns, root_allowlist |
| 2. 是否脚本 | 文件元数据 | Move / Keep | script_extensions, script_exclude_dirs |
| 3. 服务运行 | 服务状态 | Running / Stopped | service_indicators |
| 4. 操作安全 | 操作 + 文件 | Safe / Unsafe | safety |
| 5. 后台进程 | 文件快照对比 | Stable / Recurrence | stability_check |
| 6. 异常文件名 | 文件名 | Safe handling / Direct | safety.special_filename_handling |
| 7. 模式推断 | 文件元数据 | Inferred garbage / Keep | detection |

**所有决策均通过配置驱动，无硬编码判断逻辑。**
