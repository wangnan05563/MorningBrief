来源：T01845（经 T01922 真机物料取证时顺带发现，非档位问题，独立成单）

【现象（实测数据，可直接复核）】
自有 COS 上已发布成品的**实际音频时长**比库里 `episode.duration` 长，且偏差不是固定值：

| 期号 | 成品文件实测 | DB `episode.duration` | 偏差 |
|---|---|---|---|
| ep100（20260727 游戏资讯） | 597.000s（ffprobe，9,552,918B，128012bps） | 586 | **-11s** |
| ep99（20260727 教育资讯） | 482.000s | 452 | **-30s** |

取证脚本：`_validate/t01922_cos_range.txt`（含 COS 返回的 `Content-Range: bytes 0-1/9552918`，
证明线上对象与本地下载文件大小一致，不是「下载残缺」）；
ffprobe 口径：`backend/ffmpeg/bin/ffprobe.exe -show_format`。

【为什么要单独查】
偏差 11s 与 30s 不同 → **排除「固定片尾/BGM tail 长度」这一类解释**，更像「落库时长与实际上传产物
不是同一份」：`backend/app/workflow/stitch/concat.py` 是 `duration = await get_audio_duration(final_path)`
之后才发布（`publish_service` 直接取 `episode.duration`），所以新链路应当是自洽的；这批 20260727 产物
要么走了别的写入点，要么 `final_path` 与上传到 COS 的对象不是同一文件（例如时长测量发生在
保底补齐/尾段拼接**之前**，或 `duration` 被字数反算覆盖过）。

【要做的排查（只读优先，不改数据）】
1. 用 git 时间线对齐：这批 ep99/ep100 发布时 `concat.py` / `publish_service.py` / `duration.py` 的实现
   与现在差异（`git log -p --since=2026-07-20 --until=2026-08-05 -- backend/app/workflow/stitch/concat.py backend/app/services/publish_service.py`）。
2. 全量盘点偏差分布：对库里所有有 `audio_url` 的 episode 做「ffprobe 实际时长 vs DB duration」对照
   （只读 GET 下载或 Range+尾部读取，参考 `_validate/t01845_fetch_samples.py` 的只读取证写法），
   给出偏差直方图，判断是「历史批次独有」还是「当前链路仍在发生」——**这一条决定后续要不要修链路**。
3. 若当前链路仍在发生：定位写入点并修正为「以上传产物实测时长为准」，同时给历史数据出一次
   重算脚本（`_validate/` 下，跑前先备份 `backend/data/news.db`，不改生产配置）。
4. 若只有历史批次有问题：结论落库并给出历史数据重算的口径建议，不碰链路。

【影响面（用于判断优先级）】
- 小程序收听进度/完播：`apps/miniprogram/services/audio.js` 用 `audioManager.duration`（真实文件时长）
  计算 `finalPos`/`listened_seconds`，而后端记账与 UI 用 DB 值 → 进度百分比会偏大、
  「听完」时上报秒数超过 `duration`；
- 30 分钟保底校验（见 T01657 的时长保底口径）如果读的是 DB 值，会低估成品时长、多补内容；
- 不改 `.env`、不直写库：需要写库时走管理端接口或经用户确认的迁移脚本。

【验收标准】
偏差盘点表（全量期号 × 两个口径 × 偏差）+ 明确结论（历史批次 / 现行链路）+
若修则附修复前后对照，若判定不修则在回传里写清依据。
