来源：T01845「音频无损音质极限压缩与传输效率评估」（经 T01871 档位套餐落地后转出的不可落地项，原文任务项 3）

【为什么这单存在】
T01871（提交 `c3c7200`）把码率与采样率收敛成档位套餐：`quality=96k@44100` / `standard=64k@32000`（新默认）
/ `lean=48k@32000`。但所有依据都是**离线客观指标**（segSNR/LSD/频谱截止），32kHz 与 24kHz 的起播兼容性
没有任何真机证据。T01871 因此刻意把 24kHz 挡在默认链路之外（24000 属 MPEG-2 Layer III / LSF，微信内置
播放器与部分 Android 解包器支持参差）——这个保守边界要由本单的真机结论来解除或固化。

【要做的实测（只读播放验证为主）】
1. 起播兼容矩阵：取 3 份成品（32k@32000、96k@44100，以及为对比临时再编的 64k@24000），分别在
   ① 微信小程序内置播放器（Android + iOS 各至少 2 台）② iOS Safari / 原生 AVPlayer
   ③ Android 系统播放器 + 主流第三方 App 起播。逐台记录：能否起播、首帧耗时、是否出现无声/卡帧、
   进度条时长是否与 API 返回 duration 一致。
2. HLS/AAC 分支：`build_hls_cmd` 现在从 PCM 中间态编 AAC（T01870 改的），确认 32kHz 输出下
   `.m3u8` 分片在真机上连续播放无断裂（要真机播完一段，不只看 ffprobe）。
3. 结论落库：任一档位真机不兼容 → 在 `backend/app/core/audio_profile.py` 的 `AUDIO_PROFILES` 撤掉该档
   或加注释标明「仅 Web 可用」；24kHz 若全端兼容 → 可增开 `lean=64k@24000`，并复跑
   `_validate/t01871_profile_verify.py` A 段口径对比后再定。

【硬约束（沿用 T01871，不要突破）】
- 不修改 `.env`；需要切档时用进程环境变量注入（`AUDIO_PROFILE=...`）。
- 不得用真实用户（dev 库 user id 1、2）做写入测试；频道配置改动走管理端接口，不直写库。
- **生成新音频会触发 TTS/LLM 付费链路，动手前先与作者确认预算**；若只做真机播放验证，可优先复用
  已发布旧成品（128kbps@44.1kHz）+ 本地再编样本，避免走付费链路。
- 不引入 redis/外部后端；默认 worker 数保持 1。
- 测完删除含明文 JWT 的临时产物并提示轮换。

【验收标准】
输出「档位 × 平台」兼容矩阵 + 每台设备现象（截图或录屏），并给出明确处置：哪些档位可对外、
24kHz 是否进默认候选、`lean` 是否值得暴露到频道级选择。
