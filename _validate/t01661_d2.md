背景（T01661 忙机预跑的结构性结论，绝对值待空闲机复核）：
- 无并发时全局写锁 `lock_wait=0.1ms` → 「asyncio.Lock 本身的 await 开销」这个假设**不成立**；
- 并发写时 `lock_wait` 升为第一大段（**36%（252.9ms）～48%（619ms）**，随负载波动）；
  持锁段 `lock_hold` 中位 22.6~69.1ms，其中 commit 只占约 60%，其余是 `db.refresh`；
- `profile_query` + `episode_check` 在顺序写下合计 ≈47%（94.6/201.4ms），且这两步**不需要持锁**。

结论方向：并发写的第一瓶颈不是锁原语，而是「持锁段长度 × 并发排队」。

   移出 `async with write_lock`（SQLite 单行插入后可用 `cursor.lastrowid` /
   `RETURNING` 取回 id，避免二次查询）；同理排查其它 `write_lock()` 使用点里的读后处理；
2. **查询前置**：`_get_user_profile` 与 episode 存在性校验合并为一次查询或走只读缓存，
   使请求路径上的 SQL 往返从 3 次（profile/episode/refresh）降到 1~2 次；
