## 1. 背景与目标

### 1.1 背景

T02323 对全部菜单做了只读源码走查，产出 634 条带 `file:line` 取证的问题与建议：高 142 / 中 344 / 低 148。T02336 对这批建议做全面评审后确认：**问题本身大多成立，但相当一部分「建议修法」不可直接照做**——例如 R1 的「静默丢弃」是有意设计（避免后台插入 DOM 唤醒最小化窗口），R3 的简单「跳过 `***`」会与 `INSERT OR REPLACE` 的整行替换语义叠加出新的数据毁损，R7 的应急停服还牵出权限模型缺口。本 PRD 只收录**经修订后的修法**。

### 1.2 目标

| 目标 | 可度量口径 |
|---|---|
| G1 消除不可逆数据损失 | 数据维护 / 配置类页面：任何「只改非敏感字段」的保存都不改变敏感列；导入 replace 不清空未提交列；审计日志不含明文凭据 |
| G2 消除「点了没反应 / 静默失败」 | 高危动作（停服、删除、清空、审批、启停）100% 有可见结果；请求失败 100% 有页内错误态或 toast（两者不重复弹） |
| G3 消除指标误读 | 所有展示指标带单位与口径；同一指标在全端刻度一致（含 `completion_rate` 的三处不同刻度） |
| G4 打通首次使用路径 | 引导可重新唤起且锚点可用；关于页/帮助文档零占位外链、零死链；小程序底部导航有文字 |
| G5 降低高频操作步数 | 高频列表页具备分页尺寸选择、筛选持久化与批量入口（按 M5/M7 清单） |

### 1.3 非目标

- 不做整体视觉重设计（配色、间距、图标体系保持现状，仅修一致性问题）。
- 不重构信息架构（除小程序 tabBar 文案与孤儿页合并等明确条目外，不改菜单分组）。
- 不引入新的图表库 / 状态管理方案 / UI 框架。
- 不做权限模型重构（`super_admin` 与二次验证作为待决策项 DEC-UX-002，不在本期直接实施）。
- 不新增独立的「通知中心」第二套体系（移动端已有消息中心，见 DEC-UX-004）。

## 4. 功能需求

### M1 数据安全与配置完整性（P0）

| ID | 需求 | 优先级 | 覆盖条目 | 说明 |
|---|---|---|---|---|
| FR-UX-101 | 敏感列禁止回写 | P0 | M14, M16, M46, F3 | 后端 `update_row` 拒绝把脱敏哨兵（`***`/`****…`）写入敏感列，且不静默跳过——返回明确错误「敏感字段请走专用重置通道」；前端编辑弹窗**不提交未变更字段**（脏字段提交），敏感列只读且不参与 payload。同一处代码的另一半（M16）：`update_row` 不得再把空串/None 当成「没填」丢弃——出现在 payload 里的有效列就是要写的列，否则「清空昵称」这类动作永远静默失效却提示成功 |
| FR-UX-102 | 导入 replace 不销毁未提交列 | P0 | M47, M48, M46 | `import_rows` 的 replace 由 `INSERT OR REPLACE` 改为 `ON CONFLICT DO UPDATE`，仅更新显式提供的列；CSV 解析改用标准 `csv` 模块（引号、换行、BOM、`\r\n`）；导入前提供 dry-run 预览（预计插入/更新/冲突行数） |
| FR-UX-103 | 审计日志脱敏 | P0 | M29 | `write_audit` 的 `detail.values` 对敏感列做脱敏（与服务端读取口径共用 `_mask_sensitive`）；删除/导入令牌改为服务端配置校验，不再前端硬编码 |
| FR-UX-104 | 配置加载失败禁存 + 重试 | P0 | H1, G2, G8 | 配置页（COS / 内网穿透 / 通知 / AI）加载失败时：显示页内错误态 + 重试，禁用保存；若保留草稿恢复，必须标记「配置未加载，保存会覆盖」并默认不恢复。禁止把默认值当已加载值提交 |

**技术要点（来自可行性复核）**
- `backend/app/services/db_admin_service.py:298-315`（update_row）与 `:434-474`（import_rows）；`routers/admin/db_admin.py:150`（审计）。
- 敏感列判定不能按「整列命中」一刀切（`ai_config.config_value` 是动态判定），需沿用 `_is_sensitive_row` 的语义。
- 前端 `views/maintenance/DatabaseAdmin.vue:390,496-503` 的 `editableColumns`/整行预填需改为脏字段 diff。

**验收（ACC-UX-101）**
1. 对 `admin_user` 任一行只改 `nickname` 保存 → `password_hash` 前后逐字节一致；保存响应不含敏感值。（原文写 `remark`，但 `admin_user` 无该列，2026-10-22 按真实表结构订正）
2. 对 `ai_config` 的非密钥行改备注 → `config_value` 不变；对密钥行保存 → 后端 400 且提示专用通道。
3. replace 导入只带 `id,title` 两列 → 目标行其余列保持原值（含 `password_hash`）。
4. 审计日志中不出现明文 key/token/secret（grep 断言）。
5. 断开后端后打开 COS 配置页 → 显示错误态、保存按钮禁用；恢复后重试成功。
6. 清空一个可空文本列（`admin_user.nickname`）后保存 → 库内该列真的变空，接口不得返回「成功而库里没动」（M16）。
7. 帮助文档「数据库维护」章节的表白名单数量、SQL 能力表述与代码一致（白名单数量按 `ALLOWED_TABLES` 计，SQL 查询入口不存在）（M80）。
8. AI 服务页把 API Key 框清空后保存 → 库里密钥保持原值，且界面明确写着「留空＝不修改」并指路「恢复初始配置」（该按钮调 `POST /ai/reset-config`，是唯一真会清空 `llm_api_key` 的通道）；`_normalize_*` 与 COS 的 `update_config` docstring 不得再声称「空字符串清除」（F3）。

9. 对 LLM/TTS/图片/COS 四类凭据各执行一次**显式清除**（`POST /ai/reset-config?scope=llm|tts|image|all`、`POST /cos/reset-config`）→ 断言**库里该行确实没了**（不是只看返回码），且进程内 Settings 已回退到 .env 默认值、旧密钥不可再用；COS 只清 SecretId/SecretKey，地域/桶/CDN 保留；清除动作落审计且 detail 不含明文；界面每条「要作废请点 X」文案都能在本页找到名为 X 的按钮（T02919）。

> F3 的修复只统一了口径（留空＝不修改），**没有**、也不应该实现「留空即删除」——前端把脱敏值折算成空串回传
> （`AIConfig.vue` 的 `key.startsWith('****') ? '' : key`），后端一旦把空串当清除，只改 base_url 就会抹掉线上凭据。
> 当时留下的两个缺口分别派生跟踪，现状如下：
> **T02919（已闭环）**——原先 `reset-config` 只清 `LLM_RESET_KEYS` 四项，TTS/图片/COS 的凭据没有任何可操作清除入口，
> 且 TTS/图片页签的「点『恢复初始配置』」是错误指引。现按「显式清除标记」裁决补齐：AI 侧 `scope=llm|tts|image|all`、
> COS 侧新增 `POST /cos/reset-config`，两者都是删行 + Settings 回退 + 落审计（detail 只记 key 名），
> 三处 `.field-tip` 与 COS 提示改为指向各自真实存在的清除按钮；「留空即删除」明确不做（理由见上一段）。
> **T02920**（按 M80 的门禁做法——数字从源码派生、不写死——全量复核 `Help.vue` 其余章节，
> 已实测「数据统计」章节列出的**收藏数、反馈数**两个指标在后端 `OVERVIEW_METRICS` 里不存在，
> 且 COS 部署步骤给出的 `python jmeter_test/verify_cos.py` 实际位于 `scripts/jmeter_test/`）。

### M2 高危动作可用性与破坏性操作防护（P0）

| ID | 需求 | 优先级 | 覆盖条目 | 说明 |
|---|---|---|---|---|
| FR-UX-201 | 应急停服可用性与状态可信 | P0 | I54, I55 | 修复 `reason` 取值作用域错误；状态读取失败显示「状态未知」而非「运行正常」；停服动作幂等（已停服时不再重复写审计）；停服后提供恢复入口与倒计时 |
| FR-UX-202 | 破坏性操作确认规范 | P0 | I1, I2, I42, I45, H9, J60, M33, M58, M59, M95, C10, M31, M32, M37, C56, D24 | 统一为：动作名 + 影响对象 + 条数/范围 + 不可逆声明；批量与高风险动作要求输入确认词（表名/`DELETE`）；删除预览必须与真实级联一致，预览失败不得降级为空确认；移动端「通过」与「一键全部通过」补二次确认并展示频道分布；素材编辑不得把标题/正文/来源从非空清成空白（C56，来源是讲书稿按书聚合键），且编辑弹窗里能看到的列必须真的可写——`source` 曾不在 PUT 请求模型里、被 pydantic 静默丢弃，属同一单的另一半；排期日历同位同日重叠必须可见（D24：角标 + 折叠清单，不得后写覆盖前写） |
| FR-UX-203 | 广告启停链路修复 | P0 | D14 | PC 端提供「停用」；`PUT /ads/placements/{id}` 不再 500；C 端 `get_active_placements` 过滤 `enabled`，确保停用即不播 |
| FR-UX-204 | 自动审批护栏 | P0 | G13 | 三条规则改为「默认校验、显式关闭才跳过」；开启前要求勾选风险确认；记录每次自动通过的命中规则 |
| FR-UX-205 | 上传/覆盖类动作可回退 | P1 | H9, J60 | 同名文件先检测并确认；删除/清空展示影响条数；提供最近删除/回收站或至少操作前快照提示 |

**验收（ACC-UX-201）**
1. 移动端应急停服：填写原因 → 确认 → 状态变为停服且成功提示；重复点击不产生第二条审计。
2. 停服状态接口失败时，横幅显示「状态未知」且不显示绿色正常运行。
3. PC 广告规则「停用」后，该投放不再出现在 `get_active_placements` 的生效结果里（服务层断言；
   C 端拼接音频读的就是这个调用，并没有独立的 HTTP 接口——2026-10-22 按实测订正原「C 端接口」口径）。
4. 删除频道确认框展示级联影响（书单 N 本、素材 N 条）；预览接口失败时禁止提交。
5. 素材编辑把标题/正文清空后提交 → 后端 400 且库里原值保持不变（不是「提示成功但内容没了」）；原值本就为空的行仍可正常保存；改书名要真的写进库（C56）。
6. 排期日历同一广告位同日叠了两条投放 → 日历出现「+N 条重叠」角标，tooltip 列出被折叠的那条；主显优先是启用中的投放（D24）。

### M3 反馈通道与失败可见性（P0→P1）

| ID | 需求 | 优先级 | 覆盖条目 | 说明 |
|---|---|---|---|---|
| FR-UX-301 | 可见性感知的反馈队列 | P0 | D78, A16, A19, E1 | 保留「页面隐藏时不插入 DOM」的既有意图；改为 FIFO 入队（去重、上限 5 条、TTL 60s），在 `visibilitychange` 恢复且 `_isRestoring` 结束后**聚合补发**；`confirm/prompt` 保持 reject、绝不回放；`loading` 不入队 |
| FR-UX-302 | 列表/详情错误态与重试 | P1 | C5, J32, M54, G2, E1, D35, B21, D25, C73, I15, M71, J4, J16, J38, J39, J47, J106 | 请求失败与「真的没有数据」可区分：页内错误态 + 重试按钮；空数据不画 0 折线（`hasTrend` 用实际数据点判断）。同一口径延伸到「会声称一件事实」的非列表块：日历不得在失败时继续渲染「—」（读作本月无排期）、进度/状态块不得复用上一对象的残留值或用 `0` 兜住失败；页内已有旧数据时，错误态须改口为「上次成功加载的数据，可能已过期」而不是「没有数据」。小程序同型（J4/J16/J38/J39/J47/J106：八页「失败即空态」）走同一判据——失败态与空态必须是两个分支，且失败态自带重试 |
| FR-UX-303 | 提示去重与单一出口 | P1 | F27, G18, M67 | 拦截器已弹的错误，局部 catch 不再二次弹；同一错误 2 秒内去重 |
| FR-UX-304 | 登录失败可见 | P0 | A19 | 登录页 401/失败必须给出可见原因（不再依赖拦截器跳过登录页）；失败后保留输入并聚焦密码框 |
| FR-UX-305 | 界面不得声称未发生的事 | P1 | C16, C43, E11, H8, M2, F2, C91 | 与 302 相对：302 管「失败被说成没有数据」，本条管「操作被说成按用户意图发生了」。四类不得静默：① 复位/恢复不彻底（C16 表单残留串进下一个对象、F2 本地草稿顶掉线上值却不说明）；② 越界被静默夹取（M2 将 1800s→1200s、+150%→+100% 却报「已同步」）；③ 口径与参数面不符（C43 聚合视图忽略精确定位却留着定位提示条）；④ 动作变形或半途成功（H8 重命名无条件补尾斜杠生成 `sub1//`、C91 整本上传卡重复章后半本入库却只报无关错误）；⑤ 点击即抛错且被 Promise 吞掉（E11 缺 `h` 导入）。判据统一为：结果与请求不一致时，必须把差值说出来并给出可纠正入口 |

**验收（ACC-UX-301）**
1. 在后台标签页触发一次保存失败 → 切回页面后看到 1 条聚合提示（不重复、不丢）。
2. 页面隐藏期间不产生新的 DOM 节点（MutationObserver 断言）。
3. 断网打开队列页 → 显示「加载失败，重试」而非「暂无数据」。

## 6. 交互与文案规范

1. **错误三件套**：页内错误态（原因 + 重试）+ 一次 toast（去重）+ 控制台结构化错误；禁止静默 `catch {}`。
2. **单位规范**：时长统一 `分钟`（保留一位小数）或明确 `秒`；比率统一带 `%` 且在数据层保持 0~1；累计类指标必须标注起点。
3. **确认规范**：`动作 + 对象 + 影响条数 + 不可逆声明`；高风险要求输入确认词；预览失败禁止提交。
4. **反馈队列规范**：隐藏期间不插 DOM；恢复后聚合补发；`confirm/prompt` 不回放；loading 不排队。
5. **空态规范**：区分「无数据」与「加载失败」；空态给下一步行动（去创建/去筛选/去配置）。

### 9.1 DEC-UX-003 网关实测记录（T02528 / INT-UX-05，2026-10-22）

链路：公网 → Tailscale Funnel `https://…tailbca47.ts.net/news/` → `http://127.0.0.1:8000`。
探针服务只应答 `/_probe/slow`（睡到点再回一句话，期间不产生任何字节），其余路径立即 404，
不改 tailscale 配置、不碰业务代码。

| 请求 | origin 静默时长 | 客户端观察 | 结论 |
|---|---|---|---|
| `GET /news/admin/api/v1/_probe/slow` | 300s | `HTTP=200 time_starttransfer=300.043s total=300.044s`，响应体为 origin 原文 | 网关未在 300 秒内断流 |
| `POST` 同路径（带 JSON 体） | 200s | `HTTP=200 starttransfer=200.100s total=200.101s` | POST 与 GET 行为一致，请求体不触发额外限制 |
| `GET /_probe/fast`（对照组） | 0s | `HTTP=200 0.51s` | 请求确实打到本机 origin，排除「网关就地拒绝」这种假阴性 |
| `GET /_probe/abort`（断流恢复） | origin 不响应、直接关闭连接 | `HTTP=502 Bad Gateway`，`Content-Length: 0`，`total=0.156s`；紧接着再打一条普通请求 `HTTP=200 0.079s` | 断流是**立即显式**的（不挂住连接），且不留粘连状态、无需恢复动作 |

断流形态带来的一个真实改动：502 的响应体是空的，前端原先会把 axios 那句
`Request failed with status code 502` 直接甩给用户。`api/aiChat.js` 现在把
502/503/504 归成一句「网关到后端的连接中断（HTTP 502），稍后可点重试」。

据此：`FR-UX-701` 的时间预算瓶颈是**前端 130s**（`AI_CHAT_TIMEOUT_MS`），不是网关，
所以不必为对齐网关而改流式（流式仍属 FR-UX-702 的独立动机：停止生成要真停止）。
后端问答超时因此被允许配到 125s（留 5s 回传余量），并且——这是本条的实际改动——
`PUT /admin/api/v1/ai/config` 现在强制校验 30–125，越界整份拒收；原先这个区间只存在于
管理端输入框，直接调接口写 600 会让「后端先到点、返回可重试提示」反转为浏览器先到点。

### 9.2 INT-UX-06 应急停服并发判重实测记录（T02529，2026-10-22）

取证环境：文件型 SQLite + 与生产一致的连接参数（`check_same_thread=False`）和 PRAGMA
（WAL、`busy_timeout`、`synchronous`），每请求独立 session，经 `httpx.ASGITransport` 打真实路由。
**必须打在 HTTP 层**：缺陷正好落在「请求 A 的读」与「请求 A 的写」之间，服务层单连接串不起来。

| 场景（改前） | 实测结果 | 结论 |
|---|---|---|
| 两击 `POST /m/emergency/stop` 同时在飞 | 两次都 `code=0`、两次都 `already=false`，审计表 2 条 | 「先读状态再判重」只在请求不重叠时成立，连点等于没判重 |
| 同上，第二次停服的原因与首次不同 | 标志被第二次覆盖，首次停服的原因/时间从此查不到 | 高危操作的时间线会被一次误点抹掉 |
| 两击同时在飞（读事务升成写事务） | 后到的写**立即** `sqlite3.OperationalError: database is locked`，`busy_timeout` 不生效 | 连点换来的不只是重复审计，还有一个 500 |
| 三击同时在飞 | 3 条审计，1 条成功语义、2 条覆盖 | 重复量随连点次数线性增长 |

改法：判重下沉到**一条带条件的写语句**（compare-and-swap）——停服用
`WHERE key='maintenance_mode' AND json_extract(value,'$.on') IS NULL OR <> 1` 抢，行还不存在时再用
`INSERT … ON CONFLICT(key) DO NOTHING` 的 `rowcount` 定输赢；只有 `rowcount` 命中的那一击写审计，
`already` 由「抢没抢到」给，回给前端的状态是写完再读的那一份。恢复方向对称（只能从 `on=1` 抢），
行不存在时不补一行垃圾数据。

曾试过用项目的全局写锁 `app/core/write_gate.write_lock()` 把「判重读 + 写 + 提交」圈进同一个临界区，
**已放弃**：`asyncio.Lock` 会被第一个争用到它的事件循环钉死，而 TestClient 每个测试一个新循环，
结果是两个与本单无关的用例直接 `RuntimeError: … bound to a different event loop`。
原子性放在数据库层，既没有跨循环问题，也不依赖「单进程 workers=1」这个部署约束。

顺带查出的一个真实缺口（已在本单内补）：停服/恢复审计一直有写，但全站唯一的审计读接口
`GET /db-admin/audit-log` 硬过滤 `category='db_admin'`，而停服写的是 `category='mobile'` ——
**写了等于没写**，值班在外面停完服回头查不到是谁、因为什么。现在补了
`GET /m/emergency/audit`（`category='mobile'` + 动作白名单 `emergency_stop|emergency_resume`、
倒序、`limit` 1–100、要登录），移动端 `/m/manage/alert` 页面就地展示「谁 / 何时 / 因为什么」。

> 这个过滤缺口是系统性的：`backend/app` 下 34 处审计写入分布在 13 个 `category`，而读口只有
