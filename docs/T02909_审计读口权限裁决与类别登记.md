# 审计读口：权限裁决与类别登记（T02909）

> 一句话：**16 个审计类别全部有读口，读权限裁决为「全量管理员可读」**。
> 派生自 T02529（INT-UX-06）。工单：MTask news 二期 `T02909`。

## 1. 修复前的事实

写侧 `AuditLog(...)` 构造点 **42 处**，落在 **16 个 `category`**（T02909 修复时为
37 处 / 15 类；T03439 新增后台账号管理 `admin_user`）：

```
ad(3) admin_user(3) ai(1) audio(2) backup(3) channel(2) cos(2) db_admin(1)
maintenance(1) material(3) mobile(2) queue(4) review(5) script(1) user(2) workflow(6)
```

读侧原先只有两条硬编码查询：`db_admin_service` 的原生 SQL（`WHERE category='db_admin'`）
和 T02529 的移动端应急停服那条。高危动作（备份恢复、系统清理、强制过审、用户启停）
事后查「谁做的」只能手工 `sqlite3` 捞表——写了等于没写。

## 2. 权限裁决（已拍板）

**全量管理员可读**：任何 B 端登录态（`role=admin` 或 `role=operator`）都能按 `category`
读到全部审计，不按模块切分。实现上读口依赖 `get_current_admin` 而**不是** `require_admin`
（`backend/app/routers/admin/audit.py`）。

- 这条裁决的直接后果要写明白：`db_admin` / `backup` / `user` / `maintenance` 这四类
  敏感动作，operator 同样可读。方案 B（四类仅 admin）已被否决，理由是没有模块级权限模型，
  发明它是 DEC-UX-002 同级的改动。
- 匿名与 C 端 token 读不到：两个读点（列表、类别汇总）都是 **401**，有用例锁住。
- 既有 `/db-admin/audit-log` 保持原口径（`require_admin`）不动；新读口没有放宽它，
  它也没有成为新读口的权限依据。
- 将来若升级到模块级分权（方案 C），只需把「category → 最低角色」做成权限点查询，
  读接口与前端组件不用重写。

## 3. 读接口

| 接口 | 参数 | 口径 |
| --- | --- | --- |
| `GET /admin/api/v1/audit-logs` | `category` / `action` / `start` / `end` / `page` / `page_size` | 倒序（`created_at desc, id desc`）；`page_size` 上限 100；`category` 未登记 → **400**，不给「静默空列表」 |
| `GET /admin/api/v1/audit-logs/categories` | — | 16 个登记类别各自的条数与最近时间；**没写过也出现（count=0）**，用来分清「读不到」和「没数据」 |

```
cd backend && .venv/Scripts/python.exe -m pytest tests/test_t02909_audit_read.py -q
```

其中 `test_every_written_category_is_registered` 用 **AST** 扫描 `backend/app/**/*.py` 里

而不登记，测试直接红（用 AST 而非 grep：`category="tech"` 这类素材业务字段会被文本扫描误收）。
运行时同口径复核是 `GET /audit-logs/categories`（一次调用清点 16 类）。

## 5. 脱敏边界

- 读侧对 `detail` 复用 `db_admin_service._mask_audit_detail`，**历史明文行也在展示层过滤**
  （T02486 / T02591）：新读口不得变成第二条泄露通道。
- `detail` 不是合法 JSON（历史脏数据）时原样带出，不能整页 500。
- 写侧口径不变：`detail` 必须是 `json.dumps(...)`，不是 `str(dict)` 的 Python repr——
  repr 让读口只能整串吐出，既按字段查不到也永远没有原因可查。

## 6. 界面挂载与已知边界

- 挂了「最近 N 条」的五页：系统清理 `maintenance`、数据库管理 `backup`、审核列表 `review`、
  移动端用户管理 `user`、后台账号管理 `admin_user`（锚点 `data-guide="maintenance-audit"` /
  `backup-audit` / `review-audit` / `user-audit` / `admin-user-audit`，请求 `silent: true`，
  失败只落本块 `ListLoadError`，绝不显示成「暂无审计记录」）。
- 其余 11 个类别（含 `db_admin`，它有自己的页面）**只有接口、没有页面挂件**。

### 6.1 「为什么」（reason）口径 —— T03321 已收口

写入点共 **42 处**（AST 扫 `AuditLog(category=...)` 构造点），按「不可逆 / 影响面」分两档：

| 档位 | 判定 | 处理 |
| --- | --- | --- |
| 口径内（**38 处**） | 删除、批量删除、恢复、导入、重跑/重触发、清理、写库、覆盖上传、停用/复位、用户自助删除、后台账号增删改等 | `detail` 必须带 `reason` 键 |
| 豁免（**4 处**） | 纯配置热更新 / 可一键改回 / 只读快照 | `detail` 只需交代「对什么」 |

豁免清单（登记在 `app/core/audit_reason.py:NO_REASON_REQUIRED`，键为 `(app 相对路径, action)`）：

- `routers/admin/ads.py` / `update_placement_enabled` —— 投放启停，可逆；
- `routers/admin/backup.py` / `create` —— 只读快照，不改现有数据；
- `routers/admin/queue.py` / `update_priority` —— 排队顺序，可再调；
- `services/auto_review_service.py` / `update_auto_review_config` —— 配置热更新。

实现约定：

- 运营侧写入点沿用 `UserToggleBody.reason` 的形态——请求体 / Query **可选 `reason`，默认空串，
  不做必填**，不打断既有调用方；`detail` 统一走 `app/core/audit_reason.audit_detail()`，
  保证 **`reason` 键始终存在**（没有就是空串），读口因此不需要猜字段在不在。
- 无人工操作者的写入点（`routers/internal/workflow.py`、`auto_review_service` 自动审批、
  `account_service` 用户自助删除、`db_admin_service` / `maintenance_service` 包装函数）
  写固定来源说明：`audit_detail(..., machine="...")` 落成 `reason = "系统自动触发：<来源>"`。
  这类动作的「为什么」就是「谁触发的」，不额外收人工理由。
- 后台清理任务的 reason 随 `params` 一起落库，执行时已没有请求上下文，仍能还原原因。

复核命令（一条命令给出「口径内应带 / 实际带了多少」）：

```
cd backend && python scripts/check_audit_reason.py
```

当前基线：写入点 38 / 口径内 34 / 已带 reason 34 / 豁免 4 / 缺 0（exit 0）。
门禁同时判红两类退化：口径内漏写 reason，以及**登记了豁免却没有对应写入点**（死豁免会让口径悄悄放开）。
action 不可静态解析（包装函数把 action 当参数透传）时按口径内处理，不允许靠「解析不出来」蒙混。
