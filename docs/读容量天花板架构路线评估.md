> 结论定位：**只评估，不改代码**。事实基线全部取自实测报告与源码行号，未实测的推断显式标注「推导」。
> 关联：T01518（三档压测）→ T01579（读路径索引/缓存，已落地）→ T01608（200 并发复验）→ 本单；

| `analysis_report.md:31-40` | 10 线程（轻载） | — | — | 单接口平均 **6–30ms** |

**瓶颈定性（推导，非直接测量）**：轻载单请求约 10–20ms，饱和点 71 TPS × 14ms ≈ **1.0 核**，
与「进程 CPU 峰值 ≈1.3 核、其余 7 个逻辑核闲置」互相印证。结论：
读天花板 = **单 uvicorn 进程的事件循环算力**，不是 SQLite 读能力，也不是索引/缓存。
这也解释了 T01579（加索引 + 热读缓存）为何只降 P95、不抬 TPS 上限。

> 该推导的已知局限：10–20ms 是轻载**墙钟**服务时间，未拆分 CPU 时间与 aiosqlite 线程池等待
> （aiosqlite 走线程、GIL 仍串行）。若后续要用它做容量规划，需按 T01617 的分段归因把墙钟换成净 CPU 时间。
> —— T01617 已做分段归因，但在开发机（CPU 82–93% 占用）只能给出相对排序，净 CPU 时间仍需 T01661 空闲机复跑，见第 3 节可信度说明。
> 反向证据是充分的：进程 CPU 峰值仅 1.3 核、机器还有 7 核空闲，说明瓶颈不是整机算力而是单进程算力。

## 1. workers>1 的前置条件（进程内状态盘点）

`config.py:152-157` 写死了这个判断：「workers>1 会破坏全局写锁串行化与缓存一致性」。
逐条核对后，实际耦合项分三类，**只有第 (a) 类是真阻断**：

(a) **必须做主进程唯一化（否则重复副作用）**
- APScheduler `AsyncIOScheduler` + 10 处 `add_job`（`workflow_scheduler.py:108,209,394-489`），
  lifespan 里 `workflow_scheduler.start()`（`main.py:1068`）→ N worker = N 份定时工作流（会真花钱：LLM/TTS/COS）。
- `play_write_buffer` 每 1s flush（`play_write_buffer.py:34,90-98,121`）→ 多进程各自缓冲，写放大 N 倍但结果仍正确。
- EventBus `asyncio.create_task` 消费队列（`main.py:1094`、`core/event_bus.py:60`）→ 事件被 N 倍重复处理。
- TunnelService + daemon 线程（`main.py:1103-1118`）→ N 条隧道子进程。
- 启动期建表/迁移/seed（`main.py:953-1033`）与 **AI+COS 配置热覆盖 Settings 单例**（`main.py:1036-1052`）
  → 并发启动互相踩 DDL，且各 worker 各自覆盖自己的单例（`config.py:499` `@lru_cache get_settings`）。

(b) **可接受降级（语义变化但不产生错误数据）**
- 进程内 TTLCache + `_counters`（`cache/manager.py:43-48,135`）、access_token TTLCache
  （`content_security_service.py:29-30`）：各 worker 独立 → 命中率按 1/N 摊薄、缓存最多陈旧一个 TTL
  （`CACHE_DEFAULT_TTL_SEC=300`，路由侧 TTL 30–60s：`channels.py:20-21`、`playlogs.py:22`、`favorites.py:30`）。
- 限流 `{ip:[ts]}` dict + `asyncio.Lock`（`middleware/rate_limit.py:52-54`）→ 实际放行阈值变成 N×配置值。
- JWT 黑名单内存 set（`services/blacklist_service.py:31-32,91-120`，TTL 300s 整表重载）
  → 注销后的 token 最长 300s 仍可用（**当前单 worker 也有同一窗口**，不是新增风险，但 workers 放大陈旧面）。

(c) **不构成阻断（评估原假设需修正）**
- 全局写锁 `asyncio.Lock`（`core/write_gate.py:36`，调用点 favorites/comments/subscriptions/feedbacks/play_service 共 11 处）：
  它只是**应用层便利**。真正的写串行化由 SQLite WAL 单写者 + `busy_timeout=10000`（`config.py:144-149`、
  `database.py:56-72` 每连接注入 PRAGMA）保证。去掉进程内锁不会写坏数据，只会把「提前排队」换成「BUSY 重试」。
  写场景在 100/200 线程下错误率 43.7%/58.8%（`perf_report.md:31-32`）本来就与 workers 无关。
- **`UVICORN_WORKERS` 目前是死配置**：仅 `config.py:157` 定义 + `tts_model_manager.py:13` 注释引用，
  全仓无任何代码读取；实际入口 `launcher.py:104-111` 硬编码 `workers=1`，门禁 `perf_gate.py:208` 亦硬编码 `--workers 1`。
  → 想调 worker 数，改 `.env` 无效，这是实施第一步要修的接线问题。

## 2. 三条路线成本/收益

| 路线 | 读容量收益 | 写容量收益 | 一次性成本 | 长期成本 | 判定 |
|---|---|---|---|---|---|
| **A. workers=N 多进程** | 近线性（8 核 → 理论 5–6×，受 GIL 外 native 线程与 SQLite 文件锁折损，估 4–5×，即 ~300 TPS） | 无（写受 WAL 单写者约束） | 中：需 (a) 类角色拆分 + (b) 类语义确认 | 低：仍单文件部署，无新中间件 | **推荐（唯一与部署形态相容的扩读路线）** |
| **B. 读写分离（只读实例 + 独立写进程）** | 与 A 同源：SQLite 无跨机副本，所谓「只读实例」只能是同机同文件的 N 个只读进程 → **B 是 A 的子集**（把 A 的 leader 拆得更干净） | 无（同库单写者不变）；跨机副本需换后端，退化为 C | 中偏高 | 中 | **不单独成立，并入 A 的角色拆分** |
| **C. 换后端（Postgres/MySQL + Redis）** | 高（真连接池、真副本、共享缓存与限流） | 高（解决 43.7%/58.8% 写错误率与 `database is locked`） | 高：`database.py:28-36` NullPool → 连接池、PRAGMA 分支、FTS5 搜索（`main.py:713-739`）在 PG 无对应实现需重写 | 高：**直接摧毁部署形态**——本项目是打包 exe + 本机 `./data/news.db`（`config.py:143`、`paths.py:144-162`、`scripts/构建打包.bat`），依赖表内无 redis/aiomysql/asyncpg（`requirements.txt:7-13`） | **不做**（除非产品改为托管服务） |

补充：无 nginx 反代，公网访问走 Tailscale Funnel / cloudflared / cpolar 子进程隧道（`main.py:1099-1118`）。
`/audio`、`/channel-assets`、`/bgm`、`/avatars`、SPA 全部由同一进程 StaticFiles 托管（`main.py:1250-1316`），
即静态字节流与 API 抢同一事件循环；音频是否已全量迁 COS 需实施前核实（若仍有本地产出，A 路线收益会被静态流量吃掉一部分）。

## 3. 每请求固定开销可优化项清单（T01617 实测修订）

> **测量条件与可信度**：数据来自 `_validate/t01617_attribution.json` / `t01617_conn_cost.json`，
> 在**开发机**测得，采样期间系统 CPU 长期 82–93%（Qoder IDE + MsMpEng 实时防护 + CompatTelRunner 遥测），
> 写请求顺序延迟 900.87ms、50 并发仅 0.85 TPS，而 T01580 在空闲机同场景为 10.1 TPS ⇒ **绝对值放大约 9 倍，不可直接引用**。
> 有效结论只有**相对排序**与「哪些项根本不是大头」；绝对数值与剩余 74.9% 未解释部分由 **T01661** 复跑校准。
> 另注：分段测量每段各自新建 Session，故建连成本被重复计入下面两段 DB 数据，做加法时须只计一次。

修订后排序（原第 0 节假定「JWT/黑名单/中间件/日志是大头」——**已被实测否证**）：

1. **每请求新建连接（NullPool）≈ 40.84ms** ← 最大已定位单项。
   `database.py:29-38` 用异步引擎默认 NullPool（注释写成"SQLite 无需连接池"），每请求 checkout 新建连接、
   checkin 即关；`database.py:56-69` 的 connect 监听器**每条新连接跑 4 条 PRAGMA**。
   同一查询：新建 Session mean 42.90ms vs 复用连接 mean 2.06ms。→ 实施单 **T01662**。
2. **未解释残差 674.68ms（占写请求 74.9%）**：现有分段（鉴权 0.16 + 黑名单 2.15 + 两次 DB 127.68 +
   ORM 增量 87.74 + 地板 7.16）只解释了约 25%，其余在 handler/依赖内部，需服务端临时计时探针 + 空闲机才能定性（**T01661**）。
3. **ORM 写路径增量 ≈ 87.74ms**（同一复用连接内：ORM add+commit mean 89.04ms vs 裸 SQL INSERT+commit 1.30ms）。
   该差值含 aiosqlite 每语句线程 handoff 在高负载下的放大，**空闲机上可能塌缩到个位数 ms**，
   故本轮不建议改裸 SQL/批量写，判定权交 T01661。
4. **openid 二次查库（原列第 1，收益下调）**：token 已带 `sub`（`core/auth.py:106-111`），
   收藏/播放读路径仍每请求 `get_user_openid(db, user.user_id)`（`favorites.py:53,124,164` → `user_service.py:17-27`），
   `Favorite.user_id` 存 openid（`favorites.py:63-64`）。原估「省 64ms」把建连成本算了进去，
   第 1 项落地后**净收益约 23ms**；做法优先进程内 TTLCache，claims 方案在其后（需兼容旧 token 回退查库）。
5. **鉴权 / 黑名单 / 中间件 / 序列化 / 访问日志 —— 均非大头**：JWT 解码 0.16ms（0.0%）、
   内存黑名单 2.15ms（0.2%）、无鉴权健康检查地板 7.16ms（0.8%，已含中间件 + `jsonable_encoder` + 同步落盘，
   折半仅省 3.58ms）。原第 2/3/4 条（序列化、日志降噪、JWT）在 <3% 阈值下**跳过或降为附带清理**；
   仍值得做的是 `logging_setup.py:226-239` 文件 sink `level=DEBUG` → INFO/`enqueue=True`（零风险但收益小）。
6. **未命中读放大（本次未量化，结论不变）**：`get_today_episode` 未命中约 4–5 次查询（`content_service.py:50-134`）、
   history 4 次（154-207）、favorites 4 次（`favorites.py:53-90`）；search 在 FTS total=0 且 CJK 时降级 LIKE
   （`content_service.py:265-384`）——最贵路径。注意第 1 项建连成本按**每请求一次**计，与查询次数无关。


## 4. 「值得做」的业务规模阈值判定

| 目标读 QPS（饱和后仍需 P95<1s） | 建议动作 |
|---|---|
| **< 30** | 不动架构。当前已落地的索引 + 热读缓存（T01579）足以支撑；只做第 3 节第 1 项（连接复用，T01662）这一条零风险削减。 |
| **30–80** | 仅削减每请求固定开销（第 3 节 1/4 两项：连接复用 + openid 缓存），把单核算力换成 TPS，不引入多进程。 |
| **80–200** | 上 **路线 A-lite**：`workers=2~3` + 角色拆分（调度/隧道/缓冲收敛到主进程），可接受 (b) 类陈旧语义。**这是唯一建议投入的架构改造**。 |
| **> 200，或写侧需要真并发** | 路线 A 全量（`workers=核数`）+ 限流/黑名单挪到共享态；写侧若同时是瓶颈，才重新评估路线 C，并同步接受「exe 单机部署」形态作废。 |

判定依据：8 逻辑核 × 单 worker ~70 TPS × 0.6 折损 ≈ 330 TPS 上限（推导）。
在 200 QPS 以下，路线 A 的性价比明显优于任何换后端方案。

## 5. 推荐落地顺序（已建派生单）

1. 先接线再谈扩展：`UVICORN_WORKERS` 目前不被读取（`config.py:157` vs `launcher.py:108`），
   任何 workers 实验都必须先让配置生效并保留 `workers=1` 默认。→ 派生单 **T01659**
2. 角色拆分（调度/隧道/缓冲/迁移只在主进程）是路线 A 的真前置，成本集中在 `main.py` lifespan 一处。→ 派生单 **T01660**
3. 每请求开销削减——**T01617 实测后顺序调整**：
   - 第一顺位：**连接复用**（消除每请求 ≈41ms 建连，无需架构变更、单 worker 形态同样受益）。→ 派生单 **T01662**
   - 前置校准：现有分段只解释约 25% 的写请求耗时，且本机 CPU 污染使绝对值失真，
     须先在空闲机带临时探针复跑，才能给 T01659 的取舍阈值定案。→ 派生单 **T01661**
   - openid 缓存 / claims 与日志降噪降为后续顺位（收益分别约 23ms、3.6ms）。→ 并入 T01659
