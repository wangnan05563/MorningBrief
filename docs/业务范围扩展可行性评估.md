# 20_News / MorningBrief 架构业务范围扩展可行性评估

> 评估对象：`D:\code\otherProjects\20_News`（FastAPI + SQLite/aiosqlite 语音内容生产系统，V1.2）
> 评估问题：现有架构与功能能否扩展到更多业务范围（如专业领域资料 → 语音学习，或其他场景）
> 评估日期：2026-08-10
> 方法：基于代码实读（`backend/app/` 各层），非抽象推断

---

## 一、结论（先给结论）

**可以扩展，且对"资料/文本 → 语音产品"这一类场景高度可复用，扩展成本低、风险可控。**

核心判断：本系统本质是一套 **"内容生产流水线 + 媒体播放产品"** 的工程封装，**新闻只是它当前的"内容配方"**。新闻特有的部分（RSS 爬虫、热度排序、新闻敏感词库、广告插入、每日定时）集中在**输入与少量编排环节**；而占代码量绝大多数的 **LLM 改写、TTS 合成、音频拼接、COS 存储、审核、播放/收藏/评论/订阅、后台管理、限流预算、工作流调度** 全部是 **业务无关的通用能力**。

两个边界必须讲清楚：
1. **"换内容"容易，"换产品形态 / 换用户群体"需要重做前端皮肤**——后端约 80% 可复用，admin-web（8091 文件）+ 小程序这层是新闻专属皮肤。
2. **"单机 SQLite + 单 worker + 进程内缓存"的硬约束**（项目已确认的 V1.2 架构）决定了它适合 **单租户 / 少租户的中小规模产品**，不适合直接做多租户 SaaS 横向扩容——后者才是真正需要引入 MySQL/Redis 的场景（目前被定为 P2 非默认）。

## 三、最关键的 4 个可复用资产（为什么扩展成本低）

1. **`Channel` = 一套"内容产品配方"容器**（`app/models/channel.py`）
   每个频道自带：定时 `schedule_time`、开场白/结尾/约束/改写模板（`intro/outro/constraint/rewrite_template`）、BGM、段间静音模式、关键词过滤、RSS 源、目标时长、展示排序。意味着"法律科普频道""医学微课""财经早报"这些新业务 **本质上就是新建一个 Channel 并填不同 prompt**——运营级配置即可，不需写代码。

2. **TTS 已是插件式工厂**（`workflow/tts/tts_factory.py` + `base_provider.py`）
   `get_tts_provider()` 按配置切换 5 种引擎，`synthesizer` 只认 `Script.segments`（纯文本分段），完全不知道上游是新闻还是教材。**新增音色/引擎 = 写一个 Provider 子类 + 注册一行**。这正是"专业资料朗读"最直接的复用点。

3. **LLM 已是多供应商 OpenAI 兼容**（`ai_config_service.py` 内置 9 个预设：qwen/openai/deepseek/智谱/kimi/百度/火山/ollama/agnes）
   换模型/厂商 = 前端选预设或填 `base_url`，无代码改动。对专业领域（需要强推理或领域大模型）尤其友好。

4. **已有"手动录入素材"入口**（`routers/admin/materials.py`，`source_type="list"`）
   这直接证明系统并非只能吃 RSS——**运营可手动新增 source/title/content/url/category 素材**。要做"专业资料 → 语音"，第一步甚至不需要写爬虫，先用手动录入或加一个"文档上传解析"适配器即可跑通全链路。

## 四、扩展为新业务的 3 个真实摩擦点（必须处理的耦合）

1. **输入层是 RSS 新闻专属**
   - `Material.url` 是唯一键（爬虫去重），专业资料没有 URL；需支持"无 URL / 合成 URL"或用 `source_type=list` + 文档 hash 去重。
   - 爬虫/热度排序（`heat_score`、按品类取热度 Top-N）是新闻语义；学习场景应是"按课程大纲/章节顺序"选题，而非热度。
   - **改造量：中**。需新增"文档/资料输入适配器"，并把"选题排序"抽象成可插拔策略（热度 / 大纲顺序 / 手动指定）。

2. **默认 prompt 与文案是新闻主播口吻**
   - `rewriter.py` 的 `INTRO/OUTRO` 写死"新闻主播""今天的新闻节目"，`rewrite.txt` 默认是新闻改写。
   - 但频道级 `rewrite_template` / `intro_prompt` **已支持覆盖**——默认是新闻，每个域可全覆盖。
   - **改造量：低**。提供一套"课程/讲解"默认模板即可。

3. **"节目 = 按日定时产出"的时间模型**
   - Workflow 以 `episode_date` 为核心，调度是每日 cron；学习产品应是"课程/章节"模型，触发方式可能是"上传即生成""按课程表"。
   - 但 `workflow_scheduler` 支持手动触发，且 `Channel.schedule_time` 是按频道可配置触发——**核心调度引擎可复用，只需换"触发时机"语义**。

次要摩擦：音频拼接内嵌 `AdService`（广告插入）——学习产品关掉广告即可；敏感词库偏新闻政治类，专业内容需换词库阈值；UI 是新闻皮肤需重做。

## 五、落地蓝图：专业资料 → 语音学习（最小可行改造）

```
输入适配器（新增，约 2–4 人日）
  ├─ 文档上传解析（PDF/Word/Markdown/网页）→ 切分为 Material（source_type=list）
  ├─ 选题策略插件：按大纲顺序 / 手动指定（替换热度排序）
  └─ Material 去重键从 url 改为 (source_type, content_hash)
        ↓
复用：Channel 配方（换一套"课程"模板：intro/outro/constraint/rewrite_template/BGM）
复用：rewriter（LLM 改写，已是 OpenAI 兼容多模型）
复用：TTS 工厂（朗读音色，已 5 引擎）
复用：stitch（拼接，关广告）
复用：cos + 审核 + 播放/收藏/评论/订阅 + 后台
        ↓
前端重皮肤（约 1–2 周）：把"频道/节目/今日新闻"换成"课程/章节/资料库"
```

**不需要动的**：TTS 全部、LLM 全部、COS、审核、工作流调度引擎、限流预算、播放/订阅/评论、绝大部分后台。

## 六、其他可扩展场景（同构）

因为核心是"资料 → 语音产品"，以下场景基本是同构扩展，成本相近：
- **企业内训 / 制度宣贯语音化**：上传制度文档 → 语音课，复用文档适配器。
- **儿童 / 老人有声读物**：换音色（童声/长辈缓速）、换 intro/outro，纯配置。
- **法律法规 / 政策速读**：强专业 + 需严谨，LLM 用强推理模型（deepseek/智谱），敏感词策略收紧。
- **多语种资料朗读**：Edge/Kokoro 多语种，TTS 层天然支持。
- **播客 / 自媒体自动成片**：复用拼接 + BGM，甚至保留广告位做变现。

**非同构、不建议复用本系统**：强交互（对话式 AI 助教）、实时音视频通话、需要复杂关系检索的 RAG 问答库——这些超出"生产流水线"范畴，本系统的对话/检索能力是空白。

## 七、规模边界与风险（必须如实告知）

1. **单实例吞吐天花板**（项目已实测）：单写者 SQLite 串行提交，写 ~15 req/s、饱和 ~22–26 req/s；读 p50=16ms。适合 **单租户 / 少量租户 / 中小规模**。
2. **多租户 SaaS 化需要 MySQL/Redis**——目前被项目硬约束排除（V1.2 架构），列为 P2 非默认。若做"平台型"（多客户内容隔离 + 横向扩容），这才是真正的架构升级点，而非功能扩展。
3. **前端皮肤成本**：后端复用度高，但 admin-web（8091 文件）+ 小程序是新闻专属，新业务前端是主要工作量。
4. **敏感内容合规**：专业/医疗/法律领域内容有合规风险，需替换敏感词策略并保留人工审核（本系统已有审核链路，是加分项）。

---

## 八、一句话建议

**后端复用率约 80%，扩展为"专业资料语音学习"是低风险高回报的演进；真正的成本在前端重皮肤与输入适配层，真正的架构天花板在多租户规模化（届时再引 MySQL/Redis，而非现在）。先把"文档上传 → 语音课"的最小闭环跑通验证，再谈平台化。**
