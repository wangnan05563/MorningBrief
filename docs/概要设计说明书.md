## 1. 引言

### 1.1 编写目的

本说明书在《需求规格说明书》基础上，完成系统总体架构与模块级设计，作为后续详细设计与编码的依据。文档目标：

- 明确系统分层、模块划分与模块间职责边界；
- 给出每个核心模块的设计方案、关键流程、对外接口；
- 定义数据模型、存储方案、运行与部署架构；
- 明确错误处理、安全、性能等非功能性设计要点。

读者读完后应能够：理解系统全貌，独立承担所负责模块的详细设计与编码，并知道模块如何协作。

### 1.2 项目背景

详见《需求规格说明书》第 1.2 节。本项目核心是一套**全自动 AI 内容生产工作流**：每日凌晨爬取前一日全网资讯 → LLM 改写为可播报稿 → 云端 TTS API 语音合成 → FFmpeg 拼接三段式广告 → 人工审核后 07:00 发布到微信小程序。

V1.5 采用**混合架构**：生产端（单机 exe）+ 消费端（云函数 + COS）。生产端由 PyInstaller 打包为单机 exe，AI 工作流作为 FastAPI 内部模块函数直接调用，无跨进程 HTTP 开销；运营后台 Vue3 SPA 由 FastAPI StaticFiles 内嵌挂载；SQLite 作为业务数据库，cachetools.TTLCache 作为内存缓存，彻底脱离 MySQL/Redis/Nginx/Docker。消费端由腾讯云函数 SCF + COS 承载，满足微信小程序合法域名需公网 HTTPS 的合规要求。

### 1.5 设计原则

1. **MVP 简约**：避免过度设计，能跑通核心闭环即可，留扩展点不实现扩展功能；
2. **模块解耦**：AI 工作流各步骤独立模块，通过工作流调度服务串行编排，可独立扩展；
3. **配置驱动**：爬取源、敏感词、广告位、音色模型路径均走配置，不硬编码；
4. **可观测**：关键步骤全链路日志与状态记录，工作流可重跑、可回溯；
5. **失败安全**：任何步骤失败不阻塞整体，有重试、有告警、有备播兜底；
6. **同语言栈**：后端、AI 工作流统一 Python，降低维护与联调成本；
7. **V1.5 新增 - 用户门槛最低**：单机 exe 双击安装即用，无 Docker/MySQL/Redis/Nginx 环境依赖；通过 SQLite + 内存缓存替代独立中间件服务，让非技术用户也能部署使用；
8. **V1.5 新增 - 生产消费分离**：生产端（单机 exe）与消费端（云函数 + COS）解耦，单机离线不影响 C 端用户访问已发布节目；
9. **V1.5 新增 - 平滑回退**：数据层通过 SQLAlchemy ORM 抽象，未来如需多人协作或多机部署，可平滑回退到 V1.0 的 Docker + MySQL + Redis 架构。

## 2. 系统总体设计

### 2.1 系统架构

V1.5 采用**混合架构**：生产端（单机 exe）+ 消费端（云函数 + COS）。

- **生产端**：PyInstaller 打包的单机 exe，FastAPI 单体应用 + APScheduler + AI 工作流模块 + 运营后台 Vue3 SPA（StaticFiles 挂载）+ SQLite + 内存缓存，用户双击 Inno Setup 安装包即用；
- **消费端**：腾讯云函数 SCF（5 个函数）+ COS + CDN，承载 C 端小程序 API，满足微信合法域名需公网 HTTPS 的合规要求；
- **数据同步**：单机 exe 在审核通过后主动上传音频 + 节目元数据 JSON 到 COS，云函数直读 COS 返回给小程序。

**架构关键点**：
1. **混合架构**：生产端（单机 exe）与消费端（云函数 + COS）解耦，单机离线不影响 C 端用户访问已发布节目；
2. **零中间件依赖**：无 MySQL/Redis/Nginx/MongoDB/Elasticsearch，全部用 SQLite + 内存缓存替代；用户无需安装 Docker Desktop；
3. **TTS 云端化**：因本地 PC 无独立 GPU，TTS 模块调用阿里云语音合成 API；
4. **运营后台内嵌**：Vue3 SPA 构建产物由 FastAPI StaticFiles 挂载到 `/admin/`，无需独立 Web 服务器；
5. **扩展点**：工作流模块通过 Python 包结构隔离，数据层通过 SQLAlchemy ORM 抽象，未来如需独立部署或多机协作可平滑回退到 V1.0 架构。

| --- | --- | --- | --- | --- |

| 生产端 | SQLite 数据库 | 单机 exe 内（%APPDATA%/MorningBrief/data/news.db） | 结构化业务数据 + 爬取素材 | SQLite + aiosqlite |
| 生产端 | 内存缓存 | 单机 exe 内（进程内） | 节目列表、广告投放、限流计数、JWT 黑名单查询 | cachetools.TTLCache |
| 外部服务 | 通义千问 API | 阿里云 | LLM 改写 | OpenAI SDK 兼容 |
| 外部服务 | 阿里云 TTS API | 阿里云 | 语音合成 | 阿里云 SDK |
| 外部服务 | 腾讯云 COS+CDN | 腾讯云 | 音频/图片存储分发 | 腾讯云 COS SDK |

> 说明：
> 1. **V1.5 关键变更**：删除 Nginx、MySQL、Redis、Docker 容器；新增云函数 SCF、SQLite、内存缓存、发布服务；
> 2. **工作流模块**是 FastAPI 应用内的 Python 包，由工作流调度服务通过函数直接调用，无 HTTP 端口；
> 3. **运营后台 SPA** 由 FastAPI StaticFiles 挂载到 `/admin/`，运营人员通过浏览器访问 `http://127.0.0.1:8000/admin/`；
> 4. MVP 阶段不引入 MongoDB（素材改存 SQLite）和 Elasticsearch（审计日志延后到二期 SQLite audit_log 表）；
> 5. feedback 表延后到二期（C 端反馈由云函数写入 COS 对象）。

### 2.4 关键设计决策

| 决策点 | 方案 | 理由 |
| --- | --- | --- |
| **V1.5 混合架构** | 生产端（单机 exe）+ 消费端（云函数 + COS）分离 | 微信小程序合法域名需公网 HTTPS，单机 exe 无法满足；云函数承载 C 端 API，单机 exe 仅负责生产与审核，单机离线不影响 C 端已发布节目 |
| **V1.5 单机 exe 打包** | PyInstaller 目录模式 + Inno Setup 安装包，参考 17_xianyu 项目 | 降低用户安装/使用/维护门槛：双击安装即用，无需 Docker Desktop / MySQL / Redis / Nginx 等环境依赖 |
| **V1.5 SQLite 替代 MySQL** | SQLite（aiosqlite 驱动）作为业务数据库，文件存于 `%APPDATA%/MorningBrief/data/news.db` | 单机单用户场景无需独立数据库服务；SQLAlchemy ORM 抽象保证未来可平滑回退到 MySQL；零运维 |
| **V1.5 内存缓存替代 Redis** | cachetools.TTLCache 内存字典 + SQLite 表（JWT 黑名单、爬虫去重等需持久化的场景） | 单机场景无高并发需求，内存字典足够；需持久化的少量数据（如 JWT 黑名单）用 SQLite 表承载；零中间件 |
| **V1.5 脱离 Nginx** | FastAPI 直接暴露 8000 端口 + StaticFiles 挂载运营后台 SPA | 单机场景无反代需求；运营后台 SPA 由 FastAPI StaticFiles 挂载到 `/admin/`，无需独立 Web 服务器 |
| **V1.5 脱离 Docker** | 移除 docker-compose，直接 PyInstaller 打包为 exe | 单机单用户无需容器化；Inno Setup 安装包体验优于 Docker 部署 |
| **V1.5 爬虫轻量化** | httpx + feedparser + newspaper3k 替代 Scrapy + Playwright | MVP 仅爬 RSS + 列表页，无需浏览器渲染；降低 PyInstaller 打包复杂度（Playwright 二进制文件巨大） |
| 单机部署 | 普通 PC 机单机部署（i7-1165G7/4C8T/48G），单机 exe 直接运行 | 用户实际硬件为 HP EliteBook 840 G8 笔记本，无独立 GPU；MVP 流量低，单机足够；降低运维与硬件成本 |
| 单体应用 | AI 工作流（爬虫/LLM/TTS/拼接）作为 FastAPI 应用内模块，函数直接调用 | 工作流是固定串行流程，无独立扩展需求；同机跨进程 HTTP 是纯开销；单体应用减少跨进程调试成本 |
| TTS 云端化 | 弃用本地 CosyVoice，改用阿里云语音合成 API | 本地 PC 无独立 GPU，CosyVoice CPU 推理需 30+ 分钟不可接受；云端 API 单次合成 1-2 分钟，按调用付费成本低 |
| LLM 调用 | 直接用通义千问 SDK + tenacity 重试，不复用 `@wiki/harness` | LLM 改写是单次并发调用，不是 Agent loop；harness 的 state/budget/hooks 在 MVP 无价值；为复用而复用反而增加 6 个模块维护成本 |
| 工作流编排 | APScheduler 嵌入 FastAPI 进程 + 函数直接调用工作流模块 | MVP 工作流步骤少且强顺序依赖，无需引入 Airflow 增加复杂度；函数调用零开销 |
| 数据库简化 | 仅用 SQLite，不引入 MongoDB | 爬取素材结构简单，SQLite 足够；少一个数据库少一份运维成本 |
| LLM 部署 | MVP 用通义千问 API，后续可切自研 Qwen2.5 | API 调用零运维成本，自研部署需 GPU 机器 |
| 音频拼接 | FFmpeg 命令行调用 | 业界标准，无需自研 |
| 任务幂等 | 工作流每步带 workflow_id + step + 状态记录 | 支持失败重跑、断点续跑 |

| 节目与审核关系 | 工作流拼接完成 → 创建 review 记录（含稿件ID、音频URL）→ 审核通过 → 创建 episode 记录并发布 | episode 仅在确认发布时创建，避免脏数据 |

| MVP 范围裁剪 | feedback 表、audit_log 表延后到二期 | MVP 聚焦核心闭环（爬取→改写→合成→发布），非核心功能延后 |

## 3. AI 工作流模块设计

AI 工作流是系统核心，由工作流调度服务统一编排，依次调用应用内的 4 个工作流模块（爬虫/LLM/TTS/拼接）。模块间通过 Python 函数直接调用，无 HTTP 开销。

### 3.1 工作流调度服务

#### 3.1.1 职责

- 接收 Cron 触发或手动触发，创建工作流实例；
- 按顺序通过函数调用执行爬虫→LLM→TTS→拼接模块；
- 记录每步执行状态、耗时、错误；
- 失败重试与告警；
- 支持断点续跑与手动重跑；
- 06:30 检查审核状态，未通过则启用备播。

#### 3.1.2 工作流状态机

工作流实例状态：

```
┌─────────┐     ┌─────────┐     ┌─────────┐
│ created │────▶│ running │────▶│ success │
└─────────┘     └────┬────┘     └─────────┘
                     │
                     │ 失败且重试耗尽
                     ▼
                ┌─────────┐
                │ failed  │
                └─────────┘
```

工作流步骤状态：

```
┌─────────┐     ┌─────────┐     ┌─────────┐
│ pending │────▶│ running │────▶│ success │
└─────────┘     └────┬────┘     └─────────┘
                     │
                     │ 失败
                     ▼
                ┌──────────┐     ┌─────────┐
                │ retrying │────▶│ failed  │
                └──────────┘     └─────────┘
                     │
                     │ 重试成功
                     ▼
                ┌─────────┐
                │ success │
                └─────────┘
```

#### 3.1.3 调度流程

```
1. APScheduler 每日 05:00 触发
2. 调度服务创建 workflow 实例（status=running）
3. 依次执行步骤（每步失败重试 3 次，间隔 5 分钟）：
   step1: crawl   → 调用 crawler.run() 函数
   step2: rewrite → 调用 llm.rewrite() 函数
   step3: tts     → 调用 tts.synthesize() 函数（内部调用云端 API）
   step4: stitch  → 调用 stitch.concat() 函数
   step5: review  → 创建 review 记录，通知运营，等待人工审核
4. 审核通过后：调用内容服务创建 episode 并发布
5. 06:30 检查：若审核未通过或工作流失败 → 启用备播
6. 全流程失败：告警运营
```

#### 3.1.4 关键接口（FastAPI 应用暴露）

| 接口 | 方法 | 说明 |
| --- | --- | --- |
| `/api/internal/workflow/trigger` | POST | 触发工作流 |
| `/api/internal/workflow/{id}` | GET | 查询工作流状态 |
| `/api/internal/workflow/{id}/retry` | POST | 重跑指定步骤 |
| `/api/internal/workflow/{id}/publish` | POST | 审核通过后发布 |

#### 3.1.5 阻塞操作隔离机制

APScheduler 与 FastAPI 共享同一事件循环。工作流中存在同步阻塞调用（FFmpeg 命令行、httpx 同步请求、subprocess），若直接在 async 函数中执行会阻塞事件循环，导致 API 响应变慢。

**隔离规则**：所有同步阻塞操作必须通过 `asyncio.to_thread()` 或 `loop.run_in_executor()` 包装到独立线程执行，不占用事件循环。

```python
import asyncio
import subprocess

async def concat(workflow_id: str, date: str) -> dict:
    # FFmpeg 是同步阻塞调用，通过 to_thread 放入线程池
    result = await asyncio.to_thread(
        subprocess.run,
        ["ffmpeg", "-i", "main.mp3", "-i", "ad_mid.mp3", ...],
        capture_output=True, timeout=120
    )
    # 上传 COS 也是阻塞 I/O，同样隔离
    await asyncio.to_thread(upload_to_cos, "final.mp3", result.stdout)
    return {"final_audio_url": "...", "duration": 600}
```

**适用场景**：
- FFmpeg 音频拼接（30s+）
- httpx 同步爬虫请求（单页 2-5s）
- subprocess 命令行调用
- 大文件上传 COS（> 10MB）

**不适用场景**（已是原生 async，无需包装）：
- 通义千问 SDK 调用（AsyncOpenAI）
- 阿里云 TTS API（aiohttp）
- SQLAlchemy async session（aiosqlite）

### 3.3 LLM 改写服务

#### 3.3.1 职责

- 从爬取素材中选取 5-6 条高热度新闻；
- 改写为口语化播报稿（2000-2200 字）；
- 敏感词过滤；
- 输出分段结构与时长估算。

#### 3.3.2 处理流程

```
1. 输入：当日全部素材（50-100 篇）
2. 选题：按品类分组，每品类选 1-2 篇热度最高
   热度 = 源权威度 × 0.3 + 标题关键词热度 × 0.4 + 发布时间近度 × 0.3
3. 单条改写：每条新闻独立调用 LLM（5-6 条并发）
   - 输入：原文 + 改写 prompt
   - 输出：90 秒播报稿（约 300 字）
4. 整稿组装：开场白（30s）+ 5-6 条改写 + 结尾（30s）
5. 敏感词过滤：过词表，命中则替换或重新生成
6. 时长估算：按 210 字/分钟估算每段时长
7. 输出：稿件 + 分段 + 引用素材 URL，存入 SQLite script 表；
```

#### 3.3.3 Prompt 设计要点

- **角色设定**：「你是一位专业的新闻主播，需要将新闻改写为适合语音播报的口语化文稿」；
- **改写规则**：事实摘要 + 背景补充 + 简短评论；不允许编造；保持中性客观；
- **风格要求**：避免书面化长句；数字读法明确；不使用「据报道」「记者了解到」等书面表达；
- **输出格式**：JSON 结构（标题、正文、时长估算、引用 URL）。

#### 3.3.4 关键设计

- **LLM 调用幂等**：相同输入 + 相同 seed 生成相同输出，便于重试；
- **并发改写**：5-6 条新闻并发调用 LLM，总耗时 < 60s；
- **超时控制**：单条 LLM 调用 30s 超时，失败重试 2 次；
- **成本控制**：MVP 用通义千问 API，单条约 2K tokens，日成本可控；
- **敏感词双层过滤**：生成前 prompt 约束 + 生成后词表扫描；
- **重试机制**：使用 `tenacity` 库装饰器实现指数退避重试，无需自研封装。

#### 3.3.5 模块结构（应用内 Python 包）

```

│   │   ├── __init__.py

│   │   ├── filter.py          # 敏感词过滤
│   │   └── prompts/           # LLM prompt 模板
```

**改写函数示例**：

```python
from tenacity import retry, stop_after_attempt, wait_exponential
import asyncio
from openai import AsyncOpenAI  # 通义千问兼容 OpenAI SDK

client = AsyncOpenAI(api_key=settings.LLM_API_KEY, base_url="https://dashscope.aliyuncs.com/compatible-mode/v1")

@retry(stop=stop_after_attempt(3), wait=wait_exponential(min=1, max=10))
async def call_llm(prompt: str) -> str:
    """单条 LLM 调用，带重试"""
    resp = await client.chat.completions.create(
        model="qwen-max",
        messages=[{"role": "user", "content": prompt}],
        timeout=30
    )
    return resp.choices[0].message.content

async def rewrite(materials: list) -> dict:
    """并发改写 5-6 条新闻"""
    tasks = [call_llm(build_prompt(m)) for m in materials]
    results = await asyncio.gather(*tasks, return_exceptions=True)
    # 敏感词过滤、组装稿件...
    return {"script_id": ..., "segments": ...}
```

### 3.4 TTS 模块（阿里云 API）

#### 3.4.1 职责

- 将改写稿分段合成为语音；
- 调用阿里云语音合成 API；
- 输出 MP3 文件到 COS。

> **架构说明**：因单机部署无独立 GPU，TTS 模块调用阿里云语音合成 API。MVP 阶段仅接入阿里云一家供应商，未来如需切换再引入适配器抽象层。

#### 3.4.2 模块结构（应用内 Python 包）

```
app/workflow/tts/
├── __init__.py
├── synthesizer.py            # 合成调度逻辑（分段并发调用）
├── aliyun_client.py          # 阿里云 TTS API 客户端
├── audio_postprocess.py      # 后处理（FFmpeg 降噪、响度归一）
└── uploader.py               # 上传 COS
```

#### 3.4.3 关键设计

- **API 选型**：阿里云语音合成（长文本 API，支持 SSML）；MVP 不做多供应商抽象，未来切换再加适配器层；
- **音色方案**：使用阿里云内置优质神经语音（如"小芸"），不做本地音色克隆；如需定制音色，阿里云支持上传样本训练（按次付费）；
- **分段合成**：按稿件 segments 分段独立调用 API，便于失败重试与时长控制；
- **并发合成**：5-6 段并发调用云端 API（无本地显存限制），单段约 10-20s，总耗时 < 2 分钟；
- **重试机制**：使用 `tenacity` 装饰器，单段失败重试 2 次；
- **音频后处理**：本地 FFmpeg 降噪、响度归一化（-16 LUFS，播客标准）、去静音；
- **输出格式**：MP3 128kbps 44.1kHz 单声道；
- **时长校验**：合成后实际时长与估算偏差 > 30s 则告警，运营手动处理；
- **成本控制**：单次 10 分钟音频约 60 万字符量级，按阿里云定价约 0.2-0.5 元/次，日成本可控。

### 3.5 音频拼接服务

#### 3.5.1 职责

- 将分段 TTS 音频拼接为完整主音频；
- 在指定位置植入广告音频；
- 输出最终成品 MP3 上传 COS。

#### 3.5.2 拼接策略

最终音频按时序结构如下（从左到右播放）：

```
┌──────┬──────────┬──────┬──────────────────────────────┬──────┬──────────┬──────┬──────────┬──────┬──────────┬──────┐
│ 0.5s │ 5-10s    │ 0.5s │ 主音频前半段 (约 4分50秒)    │ 0.5s │ 30s      │ 0.5s │ 主音频   │ 0.5s │ 10s      │ 0.5s │
│ 静音 │ 开头广告 │ 静音 │                              │ 静音 │ 中间广告 │ 静音 │ 后半段   │ 静音 │ 结尾尾版 │ 静音 │
└──────┴──────────┴──────┴──────────────────────────────┴──────┴──────────┴──────┴──────────┴──────┴──────────┴──────┘
                                                                                              │
                                                                                              └ 主音频后半段 = 主音频总长 - 5分钟
```

拼接步骤：
1. 主音频 = concat(seg0, seg1, ..., segN)（分段 TTS 输出合并）；
2. 在主音频 300s（5分钟）处插入中间广告；
3. 开头拼接：静音 + 开头广告 + 静音；
4. 结尾拼接：静音 + 结尾尾版 + 静音。

#### 3.5.3 FFmpeg 命令模板

```bash
# 1. 主音频拼接（分段 TTS 输出合并）
ffmpeg -i "concat:seg0.mp3|seg1.mp3|seg2.mp3" -acodec copy main.mp3

# 2. 中间广告插入（在 300s 处切开，插入广告后拼接）
ffmpeg -i main.mp3 -i ad_mid.mp3 \
  -filter_complex "[0:a]atrim=0:300,asetpts=PTS-STARTPTS[a1];\
                   [0:a]atrim=300,asetpts=PTS-STARTPTS[a2];\
                   [a1][1:a][a2]concat=n=3:v=0:a=1[out]" \
  -map "[out]" main_with_mid.mp3

# 3. 开头与结尾广告拼接（含静音过渡）
ffmpeg -i silence_05s.mp3 -i ad_head.mp3 -i silence_05s.mp3 \
  -i main_with_mid.mp3 -i silence_05s.mp3 -i ad_tail.mp3 -i silence_05s.mp3 \
  -filter_complex "concat=n=7:v=0:a=1[out]" -map "[out]" final.mp3
```

#### 3.5.4 关键设计

- **广告素材来源**：从广告服务查询当日生效投放，无投放则用默认自营口播；
- **格式统一**：所有音频统一码率/采样率，避免拼接爆音；
- **静音过渡**：0.5s 静音片段预生成，复用；
- **失败重试**：FFmpeg 命令失败重试 2 次；
- **校验**：拼接后总时长应在 9:30-10:30，超出则告警。

### 3.6 工作流时序

```
05:00:00  APScheduler 触发工作流
05:00:05  爬虫服务启动，爬取 50-100 篇素材（耗时约 20 分钟）
05:20:00  LLM 服务启动，基于通义千问 SDK + tenacity 并发改写 5-6 条（耗时约 1 分钟）
05:21:00  TTS 适配器调用云端 API，并发合成 5-6 段（耗时约 2 分钟）
05:23:00  音频拼接服务启动，植入广告（耗时约 30 秒）
05:23:30  审核服务创建 review 记录，通知运营（短信/企微）
05:23:30  等待人工审核（最长 1 小时 7 分钟）
06:30:00  审核截止时间
06:30:01  若审核通过：内容服务创建 episode，发布
          若审核未通过/超时：启用备播（见 3.7）
07:00:00  小程序可访问今日节目
```

> **时序对比 V1.2（本地方案）→ V1.5（云端方案）**：TTS 从本地 CosyVoice 串行 4 分钟改为云端 API 并发 2 分钟，整体工作流提前 2 分钟完成，审核窗口增加 2 分钟。

### 3.7 备播机制

当工作流失败、审核超时或审核打回且来不及重新生成时，启用备播：

```
1. 触发条件：
   - 工作流任一步骤重试耗尽仍失败
   - 06:30 审核仍未通过
2. 备播动作：
   - 查询前一日 status='published' 的 episode
   - 复用其 audio_url，创建新 episode 记录：
     date = 今日
     audio_url = 前一日 audio_url
     title = "7月7日 · 今日要闻（备播）"
     status = 'published'
     is_backup = true
   - 发布到小程序
3. 通知运营：备播已启用，需事后排查原因
```

### 3.8 发布服务设计

V1.5 新增模块：发布服务负责审核通过后将节目从单机 SQLite 同步到云端 COS，供云函数读取返回给小程序。

#### 3.8.1 职责

- 审核通过后创建/更新 `episode` 记录（SQLite）；
- 上传音频文件到 COS（`audio/{episode_id}.mp3`）；
- 上传节目元数据 JSON 到 COS（`episodes/meta/{date}.json`）；
- 更新历史列表索引 JSON（`episodes/index.json`）；
- 刷新内存缓存（TTLCache）；
- 刷新 CDN 缓存（通过腾讯云 CDN API）。

#### 3.8.2 COS 对象约定

| 对象路径 | 内容 | 写入时机 | 读取方 |
| --- | --- | --- | --- |
| `audio/{episode_id}.mp3` | 最终音频文件（含广告拼接） | 发布时上传 | 小程序播放器（CDN 分发） |
| `cover/{episode_id}.jpg` | 封面图 | 发布时上传 | 小程序首页 |
| `episodes/meta/{date}.json` | 单期节目元数据（标题、时长、品类、稿件 URL） | 发布时上传 | 云函数 /episodes/today、/episodes/{id} |
| `episodes/index.json` | 历史列表索引（最近 30 期摘要数组） | 发布时更新 | 云函数 /episodes/history |
| `playlogs/{user_id}/{episode_id}.json` | 用户播放进度 | 云函数写入 | 云函数 /playlogs/progress |
| `feedbacks/{ticket_id}.json` | 用户反馈 | 云函数写入 | 云函数 /feedbacks |
| `jwt_blacklist/{jti}.json` | C 端 JWT 黑名单 | 云函数登出时写入 | 云函数鉴权时读取 |

#### 3.8.3 发布流程

```
审核通过
   │
   ▼
1. 创建 episode 记录（SQLite，status='published'）
   │
   ▼
2. 上传音频到 COS：audio/{episode_id}.mp3
   │ 失败重试 3 次，间隔 10s
   ▼
3. 上传元数据 JSON 到 COS：episodes/meta/{date}.json
   │ 含 title/duration/categories/script_url/audio_url
   ▼
4. 更新历史索引：episodes/index.json
   │ 读取旧 index → 追加本期 → 截断保留 30 期 → 上传
   ▼
5. 刷新内存缓存（TTLCache 清除 episodes:today 等键）
   │
   ▼
6. 刷新 CDN（调用腾讯云 PurgeUrlsCache API）
   │ 失败仅告警，不阻塞（CDN 缓存自然过期）
   ▼
7. 发布完成，日志记录
```

#### 3.8.4 发布原子性与失败回滚

- **步骤 1-4 任一失败**：episode 记录回滚为 `status='publish_failed'`，运营可手动重试发布；
- **步骤 5-6 失败**：不回滚（缓存最终一致，CDN 自然过期）；
- **幂等性**：发布服务支持重复调用，COS 上传覆盖同名对象，SQLite 以 episode_id 唯一。

#### 3.8.5 对外接口

发布服务作为 FastAPI 应用内模块，通过函数调用：

```python
# app/services/publish_service.py
async def publish_episode(review_id: int) -> dict:
    """审核通过后发布节目，返回 {"episode_id": 789, "audio_url": "..."}"""
    ...
```

#### 4.4.3 鉴权逻辑

- **episodes_today / episodes_history**：无需鉴权（公开内容）；
- **episodes_detail**：无需鉴权（公开内容）；
- **playlogs_progress**：需 JWT 鉴权（仅写入自己的进度）；
- **feedbacks**：需 JWT 鉴权（仅登录用户可反馈）。

**JWT 验签流程**（云函数侧）：
1. 从请求头 `Authorization: Bearer {token}` 提取 JWT；
2. 本地验签（HMAC-SHA256，密钥由环境变量注入）；
3. 查内存缓存黑名单（冷启动时从 COS 加载，TTL 5 分钟）；
4. 未命中缓存则查 COS `jwt_blacklist/{jti}.json`；
5. 验签通过则放行，否则返回 401。

#### 4.4.4 冷启动优化

- **预置并发**：episodes_today 配置 1 个预置并发实例，降低首屏延迟；
- **依赖精简**：仅依赖 `cos-python-sdk-v5` + `pyjwt`，冷启动 < 1s；
- **黑名单缓存**：启动时加载 COS 黑名单到内存，TTL 5 分钟，避免每次请求查 COS。

| --- | --- |

| 内存 | 256 MB（episodes_today/history/detail）/ 128 MB（playlogs/feedbacks） |
| 超时 | 5s |
| 触发器 | API 网关（HTTP 触发） |
| 环境变量 | `COS_SECRET_ID`、`COS_SECRET_KEY`、`COS_BUCKET`、`COS_REGION`、`JWT_SECRET` |
| 日志 | 写入腾讯云 CLS（日志服务） |

#### 4.4.6 错误处理

- COS 读取失败：返回 404 + 友好提示（"今日节目尚未发布"）；
- JWT 验签失败：返回 401 + `{"code": 401, "message": "未授权"}`；

- 所有错误记录到 CLS 日志，便于排查。

## 6. 接口设计

### 6.1 接口规范

- **协议**：C 端接口 HTTPS（云函数自动提供），B 端接口 HTTP（单机本机回环 `http://127.0.0.1:8000`）；
- **数据格式**：JSON（UTF-8）；
- **鉴权**：`Authorization: Bearer {token}`（C 端云函数 token 与 B 端单机 token 各自独立）；
- **统一响应格式**：所有响应均包装为 `{ "code": 0, "message": "success", "data": {...} }`；成功时 code=0，失败时 code 为非零错误码；
- **HTTP 状态码**：200（成功）、400（参数错误）、401（未登录）、403（无权限）、404（资源不存在）、429（限流）、500（服务内部错误）；
- **分页**：`?page=1&size=20`，响应 data 为 `{ "total": N, "list": [...] }`。

> **V1.5 变更**：C 端接口从单机后端迁移到云函数，接口规格保持兼容；B 端接口仅在单机 exe 内提供（本机回环，无需 HTTPS）。

### 7.2 表结构设计（SQLite）

> **V1.5 SQLite 通用改造规则**：
> - `BIGINT PRIMARY KEY AUTO_INCREMENT` → `INTEGER PRIMARY KEY AUTOINCREMENT`
> - `ENUM('a','b')` → `VARCHAR(32) NOT NULL CHECK (col IN ('a','b'))`
> - `JSON` → `TEXT`（SQLAlchemy 应用层 `JSON()` 类型自动适配 SQLite）
> - `DATETIME DEFAULT NOW()` → `DATETIME DEFAULT CURRENT_TIMESTAMP`
> - `ON UPDATE NOW()` → 移除，由应用层在 update 时手动设置
> - 外键：SQLite 默认关闭，需在连接初始化时执行 `PRAGMA foreign_keys = ON;`

### 7.3 内存缓存与持久化替代方案（V1.5 替代 Redis）

> V1.5 移除 Redis，改用 `cachetools.TTLCache` 内存缓存 + SQLite 表持久化。单机单用户场景无高并发需求，内存字典足够。

| 原 Redis Key（V1.4） | V1.5 替代方案 | 实现位置 | TTL/持久化 |
| --- | --- | --- | --- |
| `episode:today` | `cachetools.TTLCache` 内存缓存 | `app/cache.py` | TTL 1 小时，发布时主动刷新 |
| `episode:list:page:{n}` | `cachetools.TTLCache` 内存缓存 | `app/cache.py` | TTL 10 分钟，新发布时刷新第 1 页 |
| `playlog:progress:{user_id}:{episode_id}` | C 端走 COS 对象（云函数）；单机端 SQLite `play_progress` 表（备用） | 云函数 + `app/models/play_progress.py` | COS 永久；SQLite 由云函数定期同步 |
| `playlog:flush:queue` | `asyncio.Queue` 内存队列 + 后台任务批量写 `play_log` | `app/services/playlog_consumer.py` | 进程内队列 |
| `workflow:current` | 内存变量 + SQLite `workflow` 表 `status` 字段 | `app/services/workflow_scheduler.py` | 进程内变量 |
| `crawler:dedup:url` | SQLite `crawler_dedup` 表（url UNIQUE） | `app/models/crawler_dedup.py` | 持久化，7 天清理 |
| `crawler:dedup:simhash` | SQLite `crawler_dedup` 表（simhash INDEX） | `app/models/crawler_dedup.py` | 持久化，7 天清理 |
| `ad:placement:{date}` | `cachetools.TTLCache` + SQLite `ad_placement` 表 | `app/cache.py` | TTL 25 小时，每日 00:00 刷新 |
| `rate_limit:api:{user_ip}` | `cachetools.TTLCache` 滑动窗口 | `app/middleware/rate_limit.py` | TTL 1 分钟 |

## 9. 出错处理设计

### 9.1 工作流错误处理

| 步骤 | 错误场景 | 处理策略 |
| --- | --- | --- |
| 爬取 | 某源超时/失败 | 跳过该源，记录日志，继续其他源 |
| 爬取 | 全部源失败 | 重试 3 次，仍失败则告警 + 启用备播 |
| 爬取 | 素材数 < 5 | 告警，运营手动补充素材或启用备播 |
| LLM | API 超时 | 单条重试 2 次，跳过该条继续其他 |
| LLM | 全部失败 | 工作流失败，告警 + 备播 |
| LLM | 敏感词命中 | 替换或剔除该条，重新生成 |
| TTS | 单段合成失败 | 重试 2 次，跳过该段（标记缺段） |
| TTS | 全部失败 | 工作流失败，告警 + 备播 |
| 拼接 | FFmpeg 失败 | 重试 2 次，告警 + 备播 |
| 审核 | 06:30 未审核 | 自动启用备播，告警运营 |
| 审核 | 打回且来不及重生成 | 启用备播 |
| 发布 | 发布失败 | 重试 3 次，告警 |

### 9.2 服务错误处理

| 场景 | 处理 |
| --- | --- |
| API 参数校验失败 | 返回 400 + 错误明细 |
| 未登录/ token 失效 | 返回 401，前端自动重新登录 |
| 无权限 | 返回 403 |
| 资源不存在 | 返回 404 |
| 服务内部错误 | 返回 500，记录堆栈日志，不暴露给前端 |
| SQLite 数据库文件损坏 | 启动时检查完整性（PRAGMA integrity_check），损坏则从备份恢复；每日自动备份到 `%APPDATA%/MorningBrief/data/backup/` |
| SQLite 数据库锁定 | 单机单用户场景极少发生；连接池 5 + 重试 3 次 + 超时 5s |
| COS 上传失败 | 重试 3 次，告警 |
| CDN 缓存未刷新 | 调用 COS 刷新接口主动刷新，重试 2 次 |
| 云函数冷启动延迟 | SCF 预置并发 1；COS 直读无冷启动；CDN 兜底 |
| AI 工作流子服务不可达 | 工作流步骤标记 failed，重试 3 次后告警 |
| 云端 TTS API 超时 | 重试 2 次，仍失败则备播 |
| 通义千问 API 超时 | 重试 2 次，跳过该条继续其他 |
| PyInstaller 打包后路径错误 | 参考 17_xianyu paths.py 模式，区分 frozen/开发态；CI 构建后冒烟测试 |

### 9.3 前端错误处理

| 场景 | 处理 |
| --- | --- |
| 网络异常 | 显示「网络不给力，点击重试」 |
| 音频加载失败 | 显示「音频加载失败」，提供重试按钮 |
| 节目未发布 | 显示「今日节目尚未发布，敬请期待」 |

## 10. 安全设计

### 10.1 鉴权与授权

| 层 | 方案 |
| --- | --- |
| C 端 API（云函数） | V1.5 改由云函数独立鉴权：JWT token，7 天有效期；云函数侧本地验签；登出时写入 COS 对象 `jwt_blacklist/{jti}.json`（TTL=剩余有效期）；**云函数冷启动时加载黑名单到内存缓存（TTL 5 分钟），降低 COS 读取延迟**；请求校验本地验签 + 查内存缓存黑名单（未命中则查 COS |
| B 端 API（单机 exe） | JWT token + RBAC（admin/operator 两角色）；登出/强制下线写入 SQLite `jwt_blacklist` 表（user_type='admin'，expire_at=JWT 过期时间）；请求校验本地验签 + 查 SQLite 黑名单 |
| 内部 API（同机进程间） | 本地回环地址校验 + 共享密钥签名（HMAC-SHA256） |
| 微信登录 | C 端由云函数调用 `code2session`；B 端账号密码登录 |

> **V1.5 变更说明**：
> 1. C 端鉴权从单机后端迁移到云函数，JWT 签发与验签在云函数侧独立完成；单机 exe 与云函数各自独立鉴权，黑名单不共享；
> 2. B 端 JWT 黑名单从 Redis 改为 SQLite `jwt_blacklist` 表，定期清理已过期记录；
> 3. JWT 仍采用无状态模式（本地验签，性能优），仅在登出/强制下线场景写 SQLite 黑名单。校验流程：①本地验签 → ②查 SQLite 黑名单（仅 jti 命中才拒绝，QPS 低）。

### 10.2 数据安全

| 项 | 方案 |
| --- | --- |
| 密码存储 | bcrypt 加盐哈希 |
| openid 存储 | AES-256 加密存储 |
| token | JWT + 短有效期 |
| 数据库 | SQLite 文件权限控制（%APPDATA%/MorningBrief/data/news.db 仅当前用户可读写）；每日自动备份 |
| COS | 私有读写，URL 签名分发（1 小时有效期） |
| 敏感配置 | 环境变量注入（.env 文件），不入代码库；.env 不随 PyInstaller 打包 |

### 10.3 接口安全

- **HTTPS 强制**：C 端云函数自动 HTTPS；B 端单机本机回环 HTTP（仅 127.0.0.1 可访问）；
- **接口限流**：C 端云函数侧限流（单 IP 60 次/分钟，cachetools.TTLCache 滑动窗口）；B 端单机单用户无需限流；
- **防重放**：内部工作流接口带时间戳 + 签名校验（5 分钟有效期）；
- **SQL 注入**：ORM 全参数化查询，禁用字符串拼接；
- **XSS**：B 端富文本内容入库前过滤 HTML 标签；
- **CSRF**：B 端使用 SameSite Cookie + 双重提交 Token。

### 10.4 审计

- **MVP 阶段**：B 端写操作（审核通过/打回、广告投放、内容下线）写入 `review` 表的 `reviewer`/`reason`/`reviewed_at` 字段，作为简化审计；
- **二期阶段**：建独立 `audit_log` 表（详见 7.2.10），所有写操作记录操作人、时间、操作类型、目标、详情；
- **审计日志保留 1 年**；
- **审计日志不可删除**（仅追加，无 update/delete 接口）。

## 11. 性能设计

### 11.1 性能指标（继承 SRS 5.1）

| 指标 | 要求 | 设计措施 |
| --- | --- | --- |
| 小程序首屏 | ≤ 1s | 接口预加载 + CDN 静态资源 + 今日节目接口精简（不含稿件） |
| 音频起播 | ≤ 500ms | CDN 边缘节点 + 音频预加载 |
| API 响应 | P95 ≤ 200ms | 内存缓存（cachetools.TTLCache） + SQLite 索引优化 |
| TTS 合成 | ≤ 2 分钟 | 云端 API 并发合成 5-6 段（V1.2 调整，原 V1.1 为本地 GPU 5 分钟） |
| 工作流总耗时 | ≤ 25 分钟（05:00-05:25） | 各步骤优化 + 串行编排 + 云端 API 加速 |

### 11.2 缓存策略

V1.5 移除 Redis，改用 cachetools.TTLCache 内存缓存：

| 数据 | 缓存层 | TTL | 失效策略 |
| --- | --- | --- | --- |
| 今日节目 | cachetools.TTLCache（内存） | 1 小时 | 发布时主动刷新 |
| 历史列表 | cachetools.TTLCache（内存） | 10 分钟 | 新发布时刷新第 1 页 |
| 广告投放 | cachetools.TTLCache（内存） | 25 小时 | 每日 00:00 刷新 |
| 播放进度 | C 端走 COS 对象（云函数）；单机端 SQLite `play_progress` 表 | COS 永久；SQLite 实时更新 | 云函数定期同步 |
| 用户信息 | cachetools.TTLCache（内存） | 1 小时 | 更新时刷新 |
| 限流计数 | cachetools.TTLCache（内存，滑动窗口） | 1 分钟 | 自动过期 |

### 11.3 数据库优化

- **索引**：所有查询字段建索引（见各表 CREATE INDEX）；
- **分页**：列表查询强制分页，单页 ≤ 20 条；
- **连接池**：SQLAlchemy 连接池，大小 5（SQLite 单机单用户场景足够）；
- **WAL 模式**：启用 `PRAGMA journal_mode=WAL;` 提升并发读写性能；
- **外键约束**：连接初始化时执行 `PRAGMA foreign_keys = ON;`；
- **完整性检查**：启动时 `PRAGMA integrity_check;`，每日自动备份；
- **读写分离**：MVP 单库，SQLite 无读写分离需求。

### 11.4 CDN 优化

- **音频文件**：CDN 全网分发，缓存 7 天；
- **封面图**：CDN 缓存 30 天；
- **刷新策略**：新发布节目主动调用 CDN 刷新接口；
- **回源**：仅首次访问回源 COS。

| 用户安装步骤数 | 安装 Docker Desktop → 启动 docker-compose → 等待容器就绪（约 5 步） | 双击 Inno Setup 安装包 → 完成（1 步） | 减少 80% |
| 环境依赖组件数 | Docker Desktop + MySQL + Redis + Nginx（4 个） | 无（全部内嵌于 exe） | 减少 100% |
| 内存峰值 | 约 3-3.5 GB（4 容器合计） | 约 2-3 GB（单进程） | 降低约 40% |
| 磁盘需求 | 约 5 GB（Docker 镜像 + 数据） | 约 500 MB（exe + SQLite + 日志） | 降低约 90% |
| Docker 容器数 | 4 个 | 0 个 | 减少 100% |
| 独立中间件服务数 | MySQL + Redis + Nginx（3 个） | 0 个（SQLite + 内存缓存内嵌） | 减少 100% |

| 打包二进制体积 | 不适用（Docker 部署） | 约 200-300 MB（PyInstaller 目录模式） | - |

#### 13.9.3 风险与缓解

| 风险 | 缓解措施 |
| --- | --- |
| 单机 exe 离线时无法生产新节目 | 已通过混合架构缓解：C 端消费已发布节目不受影响；生产端可随时重启 |
| 云函数 SCF 冷启动延迟 | 预留并发实例；C 端首屏展示骨架屏，降低用户感知 |
| SQLite 单机并发写入限制 | 启用 WAL 模式；单机单用户场景无高并发；写操作串行化 |
| PyInstaller 打包路径问题 | 参考 17_xianyu 成熟方案；spec 文件显式声明 hiddenimports 与 datas |
| 腾讯云 SCF/COS 配置门槛 | 提供详细配置文档与 scf/ 目录下的函数模板；.env 中预置配置项 |

#### 13.9.4 平滑回退路径

V1.5 数据层通过 SQLAlchemy ORM 抽象，未来如需多人协作或多机部署，可平滑回退到 V1.0 的 Docker + MySQL + Redis 架构：

1. **ORM 抽象**：业务代码不直接写 SQLite 方言，通过 SQLAlchemy ORM 操作，切换数据库仅改连接串；
2. **缓存接口抽象**：内存缓存（TTLCache）与 Redis 客户端可互换，业务代码面向 `CacheInterface` 编程；
3. **C 端 API 可迁移**：云函数 SCF 可平滑迁移到 FastAPI 路由（保持接口契约一致），仅改部署形态；
4. **配置驱动**：数据库类型、缓存类型、部署形态均由 .env 配置驱动，切换不改代码。

**修订原则**：V1.5 为架构层面的重大调整，核心目标是降低用户使用门槛（双击 exe 安装即用）并满足微信小程序合法域名合规要求（云函数承载 C 端）。所有修订均围绕"用户门槛最低、生产消费分离、平滑回退"三项 V1.5 新增设计原则展开。
