## 一、差距分析

## 二、根因定位

1. **时长无目标约束**：`min_duration_sec` 未配置，缺少 30 分钟保底，重写阶段无字数/时长强制门槛。
2. **选材未隔离书源**：`referenced_materials` 混入 `culture.people.com.cn` 的两条外链（《大敦煌》纪录片、《非来不可》节目），说明书池模式仍引入了书籍之外的新闻素材，直接被写进正文。
3. **重写提示词被通用新闻风格污染**：频道 `rewrite_template` 为书籍解读要求，但实际生成的段落大量套用财经/数码新闻衔接句式，LLM 把无关话题与书籍生硬拼接。
4. **未注入书目元数据与目录约束**：① 未强制作者信息前置校验，导致"余华→昆德拉"错配；② 未把书本目录作为顺序约束，导致 LLM 自由重组、跨章跳跃、只吃序章。
5. **连载节奏未铺开**：全书约 12 万字、106 段素材，单期仅用约 9 段、3318 字，远未利用素材池支撑内容深度。

## 三、可落地改善建议（供执行团队落实）

### A. 解决时长不足（提量）
1. 在频道配置将 `channel.min_duration_sec` 设为 **1800**（30 分钟保底），使重写阶段以"目标时长≈1800s"为硬约束。
2. 重写阶段增加**目标字数下限**校验：按 250 字/min 折算约 7500 字；`script.total_words` 低于阈值或预估时长 < 保底×0.9 时，触发自动扩稿（回到 LLM 以新增材料重写一轮）或直接失败告警。
3. 启用**多期连载**：按目录顺序每期覆盖书中连续若干章（如 8-12 段/期，约 4-5 期读完），`book_pool_cursor` 已具备游标，把单期内容做深做足。
4. 素材充足：全书 106 段在库，扩稿时优先拉取**书内后续章节**而非外部新闻。

### B. 修复段落衔接
5. 在 `rewrite_template` 中**显式禁止**金融/地产/数码/游戏新闻套话（如"视线转向产业资本动向""从开发商动态来看""另一款大作""硬件之外软件也有看点""顺带提一下一款新作"），要求以书籍逻辑过渡词衔接。
6. 增加**"书籍专属上下文"注入**：改写时携带书名、作者、目录供其遵循，要求每个段落必须对应当前书某一章节内容。
7. 对最终文稿做**衔接体检**：检查是否存在高频新闻套话或"引用外部非本书记载的事例"，命中则标记重审。

### C. 保证按阅读顺序 + 事实正确
8. **注入书目元数据前置校验**：书名=《我只知道人是什么》、作者=余华、出版社=译林出版社，在 LLM 输出前注入，并做作者/书名一致性抽查，杜绝"昆德拉/余华"混记。
9. 把**书本目录按顺序**作为改写的顺序约束，要求 LLM 依目录推进、不跳章；跨期连载与目录对齐。
10. 对 `referenced_materials` 增加**书源校验**：`script_mode=book_pool` 时，引用材料必须全部来自当前书（`material.source` = 书名），外链新闻一律剔除，防止《大敦煌》《非来不可》类串味。

### D. 补强质量闭环
11. 修复内容安全校验跳过问题（微信 API 40003），确保 `content_security` 真实执行；校验失败时阻断发布而非放行。
12. `review` 环节保持人工/自动审核门禁，审核通过后再落 `episode`，避免未发布内容直接外放。

## 四、结论复核

| 维度 | 结论 |
|---|---|
| 音频时长 | ❌ 实际 647s（约10.8min），仅达 30 分钟目标约 36%，且系统未设保底 |
| 段落连贯性 | ❌ 大量财经/数码新闻套话、串入书外话题，衔接断裂明显 |

**优先级建议**：先落地 A1（时长保底）+ C10（书源隔离）+ C8（作者校验）三项见效最快、代价最低；其次 B5（禁套话）与 A3（连载）提升收听体验与内容容量。

### 5.1 时长 A 阶段 —— 目标已正确施加，但 LLM 字数拖后腿
- `target_sec` = 1800 已生效（`channel9.min_duration_sec=1800` → `_fetch_channel_prompts` → 重写目标时长）。
- 但实际 `estimated_duration=1568s`（12 段 / 8624 字），263s 缺口。系统已多次触发「字数不足→硬约束重试/扩稿」，补足段追加后才到 1568s。
- **真实瓶颈是模型单段字数上限**：agnes-2.5-flash 目标每段约 1000 字，平均只产出约 650-700 字；运行时已打出告警"LLM 字数达成率低于阈值 / 建议优化 prompt 或更换模型"。
- 结论：A 阶段机制生效，其余靠模型产出能力；要逼近 1800s 需换更强模型或提高每段字数硬约束后再扩稿。

### 5.2 书源隔离 C 阶段 —— 达标
- `_filter_audiobook_sources` 生效：106 篇 pending 素材中被改写进入稿件的段落全部锚定书名「我只知道人是什么」，0 例书外素材混入（对比改造前 `culture.people.com.cn` 外链串味，已根治）。

### 5.3 书外套话 B 阶段 —— 显著减少但未清零
- 秒杀类禁语（产业资本/开发商/3A大作/硬件软件/顺带提）已大幅收敛，但复检仍命中：
  - `seq5`「…开发商…」（书外套话残留）
  - `seq9`「从另一个平台来看，一部没有字幕的电影…」
  - 改造前那些「视线转向产业资本动向 / 换个赛道 / 再来看一条订阅服务变化」仍有零星漏网。
- 结论：B 阶段 prompt 规则有效但非 100% 可靠，建议在改写后处理再加一层**禁语清洗/重写**兜底（比依赖 prompt 更稳）。

### 5.4 内容安全合并 —— 发现真实 bug（阻断 D 门禁正向验证，但 fail-closed）
- `content_security_service.check_text` 第 213 行 `item.get("suggest")` 崩溃：当微信 `msgSecCheck` 合法返回（errcode=0）且 `result` 字段为**字符串**时，`for item in result` 逐字符迭代导致 `AttributeError: 'str' object has no attribute 'get'`。
- 该异常被捕获为"告警不阻断"，但 `content_security` **永远无法写回** rewrite 结果（实测 `content_security={}`）。
- 后果：D 门禁走到 `_check_content_safe` 的 `if not content_security: return False, "未执行内容安全检测"` 分支 → **自动审批被永久禁用**（fail-closed，安全，但并非设计意图的"skipped→人工"路径，而是"无结果→人工"）。
- **建议修复**：`check_text` 中对 `data.get("result")` 做类型防护（非 list 按空处理或解析），使合并 `content_security` 成功，从而真正走通"skipped→阻断/通过→放行"语义。

### 5.5 作者归属 —— ❌ 未随 B/C 改善，仍需修复
- 同上，`seq3` 改为「米兰·昆德拉」、`seq5/seq6「余华 / 孙频」`、原始 raw 日志还出现「余秋雨」——同一本书复检轮次内多位作者交替，属事实性错误红线。

### 5.6 复检产物与复现
- 隔离库：`_validate/news_validate.db`（channel9=1800）；报告：`_validate/report.json`
- 复现脚本：`_tmp_run_workflow.py`（注入 ai_config→settings、短路 tts/stitch/通知）

### 复检结论
改造相对原始问题改善显著（时长 36%→87%、书源隔离根治、门禁 fail-closed 安全），
