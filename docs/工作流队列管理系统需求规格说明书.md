## 1. 引言

### 1.1 编写目的

本说明书为「MorningBrief 工作流队列管理系统」提供明确、可验证的设计与开发依据。系统在现有单工作流串行执行架构基础上，引入多频道、优先级队列、并行执行与可视化队列管理能力，解决以下问题：

1. **并发冲突直接拒绝**：现有 `WorkflowScheduler` 使用 TTLCache 互斥锁，同一时间仅允许 1 个工作流运行，cron 与手动触发并发时直接抛 `WorkflowConflictError`，无排队机制；
2. **无多频道支持**：现有 `Workflow` 模型无频道概念，无法按内容分类（科技/财经/娱乐等）独立产出节目；
3. **无优先级与执行模式配置**：任务无优先级，无法配置串行/并行执行模式与最大并发数；
4. **队列状态不可见**：`WorkflowStatus` 仅含 `running/success/failed/cancelled`，缺少 `queued` 等队列状态，前端无队列管理界面。

### 1.2 项目背景

MorningBrief V1.2 采用混合架构：单机 exe（PyInstaller + SQLite + TTLCache）负责 AI 内容生产与运营后台；云函数 SCF + COS 承载 C 端小程序 API。现有工作流调度为「单频道、单工作流、串行执行」模式：

- 每日 05:00 cron 触发单一工作流，串行执行 crawl → rewrite → tts → stitch → review 五步；
- TTLCache 互斥锁确保同一时间仅 1 个工作流运行，并发触发直接拒绝；
- `WorkflowService` 提供查询、手动触发、重跑、批量删除能力，但无队列管理。

随着内容品类扩展需求，运营希望按内容分类频道独立产出节目（如「科技早报」「财经速递」），并支持多频道工作流并发执行以提升生产效率。本子系统在不动摇 V1.2 混合架构的前提下，为工作流调度层引入队列、频道、优先级与可视化能力。

### 1.3 术语与缩略语

| 术语 | 含义 |
| --- | --- |
| Channel | 新闻内容分类频道（如科技/财经/娱乐），作为工作流分组标签 |
| PriorityQueue | 优先级队列，按 (priority DESC, created_at ASC) 排序出队 |
| Semaphore | 信号量，限制同时执行的工作流数量 |
| 执行模式 | serial（串行，max_concurrent=1）或 parallel（并行，max_concurrent=N） |
| 队列状态 | queued（等待中）/ running（执行中）/ success / failed / cancelled |

### 1.4 设计原则

1. **兼容现有架构**：不改变 V1.2 混合架构（单机 exe + SQLite + TTLCache + 云函数），仅在调度层增强；
2. **数据库权威**：队列状态以 SQLite `workflow` 表为权威源，TTLCache 仅做互斥与计数，重启后从 DB 恢复；
3. **最小侵入**：复用现有 `_run_workflow` / `_run_step` / EventBus / NotifierHub 等机制，仅替换触发入口与并发控制；
4. **轻量频道**：Channel 仅作为分组标签（id/name/description/is_active），不绑定爬虫源/TTS音色/LLM模型配置，后续迭代扩展；
5. **配置驱动**：执行模式与并发数存 SQLite `queue_config` 表，管理员可热修改，无需重启。

### 1.5 适用范围

本说明书仅覆盖工作流队列管理子系统。现有 AI 工作流的 crawl/rewrite/tts/stitch/review 内部逻辑、小程序端、云函数、广告管理、审核流程等不在本说明书范围。

### 3.2 功能需求清单

#### FR-QUEUE-01：队列机制与优先级调度

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 描述 | 将工作流触发从「直接执行」改为「入队 + 后台消费」，支持任务优先级 |
| 入队规则 | `trigger_workflow(channel_id, priority)` 写 DB (status=queued) → 入 PriorityQueue |

## 4. 数据模型设计

### 4.1 新增 Channel 表

```sql
CREATE TABLE channel (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name VARCHAR(64) NOT NULL UNIQUE,
  description VARCHAR(256),
  is_active INT DEFAULT 1,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

### 4.2 改造 Workflow 表

```sql
-- 新增字段（ALTER TABLE 兼容历史数据）
ALTER TABLE workflow ADD COLUMN channel_id INTEGER REFERENCES channel(id);
ALTER TABLE workflow ADD COLUMN priority INT DEFAULT 5;
```

**状态枚举扩展：**

- 原: `running / success / failed / cancelled`
- 新: `queued / running / success / failed / cancelled`

**CHECK 约束迁移策略（P0-1 修复）：**

现有 [workflow.py](file:///d:/code/otherProjects/MorningBrief/backend/app/models/workflow.py) 第 48 行有 `CheckConstraint("status IN ('running', 'success', 'failed', 'cancelled')")`。SQLite 的 `Base.metadata.create_all` 对已存在的表不会修改 CHECK 约束，存量部署插入 `status='queued'` 会报 `CHECK constraint failed`。

**决策：移除 DB 层 CHECK 约束，仅靠 ORM 枚举约束。**

理由：
1. SQLite CHECK 约束对业务无实际保护价值（ORM `WorkflowStatus` 枚举已足够约束合法值）
2. 避免"创建新表 → 迁移数据 → 删旧表 → 重命名"的复杂迁移脚本
3. `priority` 字段不加 DB 层 CHECK，同样靠 ORM 层 `Field(ge=0, le=10)` 约束

实现：
1. 从 `Workflow.__table_args__` 移除 `ck_workflow_status` CHECK 约束
2. `WorkflowStatus` 枚举新增 `QUEUED = "queued"`
3. 存量部署需手动执行：`ALTER TABLE workflow DROP CHECK ck_workflow_status;`（SQLite 3.35+ 支持）

### 4.3 新增 QueueConfig 表（单行配置）

```sql
CREATE TABLE queue_config (
  id INTEGER PRIMARY KEY CHECK (id = 1),  -- 单行约束
  execution_mode VARCHAR(16) NOT NULL DEFAULT 'serial'
    CHECK (execution_mode IN ('serial', 'parallel')),
  max_concurrent INT NOT NULL DEFAULT 1
    CHECK (max_concurrent BETWEEN 1 AND 5),
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

### 4.4 改造 Episode 表（备播机制多频道适配，P0-2 修复）

多频道场景下，每个频道产出独立 episode。现有 Episode 模型无 `channel_id` 字段，备播查询 `Episode.date == today` 会匹配到多个频道的 episode，`scalar_one_or_none()` 会抛 `MultipleResultsFound`。

```sql
-- 新增字段（ALTER TABLE 兼容历史数据）
ALTER TABLE episode ADD COLUMN channel_id INTEGER REFERENCES channel(id);
```

**备播机制改造**（[workflow_scheduler.py](file:///d:/code/otherProjects/MorningBrief/backend/app/services/workflow_scheduler.py) `_check_backup` 方法）：

- 原逻辑：查 `Episode.date == today`，`scalar_one_or_none()` 取唯一 episode
- 新逻辑：按 channel_id 分组，对每个活跃频道，若该频道今日无 episode，则复用该频道前一日 episode
- 查询条件改为 `Episode.date == today AND Episode.channel_id == ?`

**影响范围说明**：
- Episode `channel_id` 字段为 nullable，历史 episode 无频道不受影响
- 发布服务 `ContentService.publish_episode` 需接收 `channel_id` 参数并写入 Episode 记录
- 小程序端按频道筛选节目为后续迭代项（见 11.3 节）

### 4.5 索引

```sql
CREATE INDEX idx_workflow_channel ON workflow(channel_id);
CREATE INDEX idx_workflow_priority ON workflow(priority);
CREATE INDEX idx_workflow_status_created ON workflow(status, started_at);
```

## 5. 后端设计

### 5.1 WorkflowScheduler 改造

| 原机制 | 新机制 |
| --- | --- |
| TTLCache 互斥锁，拒绝并发 | asyncio.PriorityQueue + asyncio.Semaphore |
| `trigger_workflow` 直接 create_task 执行 | `trigger_workflow` 入队 (status=queued) |
| 无优先级 | PriorityQueue 按 (priority DESC, created_at ASC) |
| 无并发控制 | Semaphore(max_concurrent) |
| 重启丢失排队任务 | 启动时从 DB 重建 PriorityQueue |

**核心流程：**

1. `trigger_workflow(channel_id, priority)` → `async with _trigger_lock` → 写 DB (status=queued) → 入 PriorityQueue
   - **P0-4 修复**：入队操作加 `asyncio.Lock`（`_trigger_lock`）串行化，防止多频道并发触发时 `_get_db_max_seq` 读到相同序号导致 workflow_id 冲突。入队操作仅 DB 写入 + PriorityQueue put，耗时 < 100ms，串行化不影响性能。
2. `_queue_worker` 后台协程循环：`await semaphore.acquire()` → 取队列任务 → `create_task(_run_workflow)` → 任务完成回调中释放信号量（try/finally 强制释放，防泄漏）
3. 应用启动时：`_rebuild_queue()` 从 DB 查 `status=queued` 任务，按 `priority DESC, started_at ASC` 排序后依次入队（P1-4 修复：确保同优先级按入队时间 FIFO）
4. 配置变更：`update_queue_config()` 更新 DB → 标记 `_config_dirty=True`（P1-2 修复：延迟生效策略，不立即重建 Semaphore）
5. 信号量延迟重建：`_queue_worker` 每次释放信号量后检查 `_config_dirty`，若为 True 则销毁旧 Semaphore、创建新 Semaphore(max_concurrent)，下次 acquire 使用新值

**移除项（P1-1 修复）：**
- **删除** `_run_workflow` 内部的 `workflow:lock` 互斥锁逻辑（[workflow_scheduler.py](file:///d:/code/otherProjects/MorningBrief/backend/app/services/workflow_scheduler.py) 第 279-287 行 acquire_lock、第 379-384 行 finally release_lock）
- Semaphore 已替代互斥锁的并发控制职责
- `cache.set("workflow:current", workflow_id)` 改为记录所有执行中任务 ID 集合（支持并行多任务标识）

**保留不变：**
- `_run_workflow` 内部 6 步串行编排逻辑
- `_run_step` 重试机制（3 次，5s/10s 退避）
- EventBus 事件发布
- NotifierHub 告警
- workflow_id 生成（日期 + 当日序号，DB 校正）

**备播机制改造（P0-2 修复）：**
- `_check_backup` 方法改为按 channel_id 分组查询（见 4.4 节）
- 对每个活跃频道，若该频道今日无 episode，则复用该频道前一日 episode

### 5.2 新增 Service 层

**QueueService**（队列查询与操作）：

| 方法 | 功能 |
| --- | --- |
| `get_queue_stats()` | 各状态任务数统计 |
| `list_queue_tasks(status, channel_id, priority, page, size)` | 队列任务分页列表 |
| `cancel_task(workflow_id)` | 取消排队中任务（status=queued → cancelled），同步从 PriorityQueue 移除 |
| `update_priority(workflow_id, priority)` | 修改优先级（仅 queued 状态），需从 PriorityQueue 移除旧条目后重新入队 |
| `retry_task(workflow_id)` | 重试失败任务（status=failed → queued，重新入队） |
| `get_queue_config()` | 获取执行模式配置 |
| `update_queue_config(mode, max_concurrent)` | 更新 DB + 标记 `_config_dirty`（延迟生效，见 5.1 节） |

**PriorityQueue 条目移除机制**：由于 `asyncio.PriorityQueue` 不支持随机删除，需维护 `dict[workflow_id] → 队列条目` 映射。取消/改优先级时：
1. 从映射中取出旧条目，标记为 `_cancelled=True`
2. 重新入队新条目（改优先级场景）
3. `_queue_worker` 出队时检查 `_cancelled` 标记，若为 True 则跳过

**删除排队中任务策略（P1-3 修复）：**

现有 [workflow_service.py](file:///d:/code/otherProjects/MorningBrief/backend/app/services/workflow_service.py) `batch_delete_workflows` 方法检查 `status == "running"` 拒绝删除。新增 `queued` 状态后：

- 排队中任务需先调用 `cancel_task`（status → cancelled），再删除
- 或在删除时同步从 PriorityQueue 移除（通过条目标记机制）

## 9. 风险与缓解

| 风险 | 等级 | 缓解措施 |
| --- | --- | --- |
| Semaphore 泄漏导致队列卡死 | 高 | 任务完成回调中强制释放，try/finally 包裹 |
| workflow_id 并发冲突 | 高 | 入队操作加 `asyncio.Lock` 串行化（P0-4） |
| PriorityQueue 重启丢失 | 中 | DB 为权威源，启动时按 priority DESC, started_at ASC 排序重建（P1-4） |
| Semaphore 重建竞态 | 中 | 延迟生效策略，等待当前任务完成后重建（P1-2） |
| 并行执行时 LLM/TTS API 限流 | 中 | 简化全局队列方案，遇到限流由现有重试机制兜冲 |
| SQLite 写并发瓶颈 | 低 | WAL 模式 + busy_timeout，单机场景无高并发 |
| 历史数据 channel_id 为 NULL | 低 | nullable 设计，查询时 LEFT JOIN channel |
